# PRD 작성 기준 — 실전 체크리스트

> 💡 실제 사내 PRD(세무상담 Agent PRD) 하나를 처음부터 끝까지 리뷰·재작성하며 도출한 **실전 적용 기준**. PRD 개념과 업계 표준 템플릿 비교는 [[prd-templates-and-writing-guide]] 참고 — 이 문서는 그 이론을 실제 문서에 적용하며 나온 판단 기준만 압축했다.

## 📚 용어 범례

| 약어 | 풀네임 | 의미 |
| --- | --- | --- |
| **PRD** | Product Requirements Document | 제품 요구사항 문서 (What) |
| **ERD** | Engineering Requirements Document | 기술 설계 문서 (How). FRD/FSD·Design Doc·Tech Spec·TCD와 같은 역할군 |
| **HITL** | Human-In-The-Loop | 자동 처리 중 사람에게 확인받는 지점 |
| **G/W/T** | Given/When/Then | 전제 상황 / 조건·트리거 / 기대 결과로 쓰는 인수조건 형식 |
| **Recall(재현율)** | - | 실제로 있었던 것 중 몇 개를 잡았나 |
| **Precision(정밀도)** | - | 시스템이 반응한 것 중 몇 개가 맞았나 |

---

## 1️⃣ 핵심 원칙 — PRD(What)와 ERD(How)의 경계

> 상세 배경·AI 제품 예외 근거는 [[prd-templates-and-writing-guide]]의 "AI/Agent 제품 특수 원칙" 참고. 여기선 실전 판단 기준만.

**판단 기준 한 줄**: *숫자나 조건이 등장해도, 그것이 "제품의 성공/실패 기준"이거나 "사용자 경험 결정"이면 PRD, 그걸 만족시키는 내부 메커니즘이면 ERD.*

| 항목 | PRD (What) | ERD (How) |
| --- | --- | --- |
| 성능 임계치 (예: "분류 정확도 90% 이상이어야 파일럿 통과") | ✅ 남음 | |
| 에스컬레이션 트리거 (예: "모호한 입력이 감지되면 사람에게 확인받는다") | ✅ 남음 | |
| 그 임계치를 계산하는 라벨링 스키마·평가 파이프라인 단계 | | ✅ 이동 |
| 에스컬레이션 판단을 위한 내부 상태 추적·데이터 모델 로직 | | ✅ 이동 |

---

## 2️⃣ 컴포넌트 명칭 사용 기준

**구분 테스트**: 이 이름이 "이미 존재하는 외부 실체"를 가리키는가, "이 PRD가 이번에 새로 발명한 내부 구조"인가?

| 질문 | 판단 |
| --- | --- |
| 다른 팀이 이미 갖고 있는 제품/조직 경계를 가리키는가? | → 이름을 써도 됨 |
| 이 PRD가 이번에 새로 설계하며 만들어낸 내부 구조인가? | → How임. "시스템이 ~한다"로 순화 |

### 실제 적용 사례 (세무상담 Agent PRD)

| 이름 | 판단 | 이유 |
| --- | --- | --- |
| Payroll Agent | ✅ 유지 | Payroll팀이 이미 보유한 별도 제품 — 외부 조직 경계 |
| Router | ❌ 재고 | 이 PRD가 이번에 새로 정한 내부 구조 |
| Task Agent | ❌ 재고 | 마찬가지로 이번에 정한 내부 설계 산물 |

**Before/After**

```
Before: "Router 사유 반환율 5%" 목표는 Router 오분류만 대상으로 한다
After:  이 반환율 5% 목표는 우리 시스템의 오분류만 대상으로 한다
        (Payroll Agent가 자체 판단으로 반려한 경우는 제외)
```

> ⚖️ **예외**: Router와 Task Agent를 서로 다른 팀이 각각 소유·리뷰한다면, 그때는 이름이 조직 경계를 가리키는 것이 되어 유지가 맞을 수 있다. 한 팀이 전부 담당한다면 이 예외는 적용 안 됨.

## 3️⃣ 언어 표현 기준 — 엔지니어링 용어 순화

| 원칙 | 근거 |
| --- | --- |
| 내부 동작 메커니즘을 전제로 한 단어는 순화 | 팀장·마케팅은 그 메커니즘을 몰라도 "무슨 일이 일어나는지"만 알면 충분 |
| 측정 대상 자체를 가리키는 전문용어는 순화 대신 정확한 용어 + 쉬운 병기 | 순화하면 의미 자체가 바뀌는 경우가 있음 |

### 순화 대상 (Before → After)

| Before | After | 이유 |
| --- | --- | --- |
| `timeout` | "확인이 늦어지거나 실패하면" | 내부 대기시간 메커니즘 전제 |
| `fail-closed` | "안전한 쪽으로 간주" | 보안 설계 패턴 이름 |
| "응답 성격에 따라 분기한다" | "다음과 같이 나누어 처리한다" | if-else 코드 서술 어투 |
| "맥락 매칭 로직이 실패하면" | "두 메시지가 같은 업무인지 구분하지 못하면" | 알고리즘을 직접 지칭 |
| "신급여 식별 API의 신뢰성" | "신급여 가입 여부 확인 시스템의 신뢰성" | 시스템 간 통신 방식 지칭 |
| "로깅한다" | "기록한다" | log의 영어 차용 |
| `kill switch` | "긴급 중단 장치" | 좋은 우리말 equivalent가 있어 유지 이유 약함 |

### 순화하면 안 되는 예외: `recall`

`recall`을 "정확도"로 순화하면 실제로 다른 지표(정밀도)와 혼동되어 **의미 자체가 바뀐다.**

| 지표 | 정확한 한글 용어 | 측정하는 것 |
| --- | --- | --- |
| Accuracy | 정확도 | 전체 판단 중 맞은 비율 |
| Precision | 정밀도 | 반응한 것 중 실제로 맞은 비율 |
| Recall | **재현율** (또는 "탐지율") | 실제로 있었던 것 중 잡아낸 비율 |

→ "정확도(recall)"처럼 엉뚱한 지표 이름을 갖다 붙이지 말고, "탐지율(recall)" 또는 "재현율(recall)"처럼 정확한 용어를 쉬운 말과 병기한다.

## 4️⃣ 성공지표 선택 기준 — Recall/Precision/Accuracy 중 무엇을 쓸지

**핵심 원칙**: 한쪽 지표만 쓰면 시스템이 "치팅"할 수 있다. 실제 있었던 것(recall의 분모)과 시스템이 반응한 것(precision의 분모)은 서로 다른 두 그룹이라, 하나만 보면 반대편에서 허점이 생긴다.

```
Recall만 본다면    → "애매하면 무조건 카드 만들자" (반응 남발 → 노이즈 폭탄)
Precision만 본다면 → "100% 확신할 때만 카드 만들자" (놓친 진짜 업무 재발)
```

**Accuracy가 안 맞는 경우**: 데이터가 불균형할 때(예: 진짜 업무가 희귀하고 대부분이 업무 아닌 메시지) accuracy는 "아무것도 안 해도" 높게 나오는 착시가 생긴다.

```
예: 진짜 업무 100건 / 전체 메시지 10,000건
AI가 아무것도 안 해도 → Accuracy = 99% (완전 실패인데 성공처럼 보임)
```

| 문제 유형 | 특징 | 맞는 지표 |
| --- | --- | --- |
| 희귀 이벤트 탐지 (예: Task 탐지) | 대부분이 "해당 없음" | Recall + Precision(또는 그 대리지표) |
| 강제 분류 (예: Router의 목적지 분류) | 모든 케이스가 반드시 어딘가로 분류됨 | Accuracy 사용 가능 |

> 💡 실제 사례에서는 "취소율 10% 미만" 게이트를 **precision의 대리 지표**로 쓰고 있었다 — AI가 헛발질을 많이 하면 기장담당자가 카드를 계속 취소하게 되고, 그게 취소율로 잡힌다. Recall 게이트(놓치지 않기) + 취소율 게이트(남발하지 않기)로 양쪽을 다 커버하는 구조.

## 5️⃣ Acceptance Criteria 작성 기준 — Given/When/Then, 선택적으로

| 항목 유형 | 형식 | 이유 |
| --- | --- | --- |
| 조건부 규칙 (분기가 있는 것) | ✅ G/W/T | 갈래를 명시적으로 드러내 테스트 가능하게 함 |
| 불변식 (트리거 없는 상시 규칙) | ❌ 서술 유지 | 시나리오로 억지로 만들면 부자연스러움 |
| 지표 게이트 (recall 90% 등) | ❌ 서술/표 유지 | 시나리오가 아니라 성공기준 그 자체 |

**Before (분기가 숨겨짐)**
> 급여/노무 처리 요청과 급여 시스템 문의는 신급여 가입이 확인된 경우에만 Payroll Agent로 전달한다. 미가입이면 기장담당자 업무로 간주한다.

**After (G/W/T, 갈래가 드러남)**

| Given | When | Then |
| --- | --- | --- |
| 급여 처리 요청·급여 시스템 문의 | 신급여 가입 확인됨 | Payroll Agent로 전달 |
| 급여 처리 요청·급여 시스템 문의 | 신급여 미가입 | 기장담당자 업무로 처리 |
| 급여 처리 요청·급여 시스템 문의 | 가입 확인 실패/지연 | 안전하게 미가입으로 간주 |

> ⚠️ G/W/T를 모든 항목에 남용하면 "When Router가 신급여 API를 조회하면…"처럼 내부 단계(How)가 다시 스며들 위험이 있다. 조건부 규칙에만 선택적으로 적용할 것.

## 6️⃣ 목차 항목별 필수/선택 기준 (요약)

> 목차 항목별 상세 내용·깊이·템플릿 비교는 [[prd-templates-and-writing-guide]] 4️⃣ 섹션 참고.

| 항목 | 담을 내용 | 필수/선택 |
| --- | --- | --- |
| Problem | 해결책이 아니라 문제부터. 정량 근거 최소 1개 | 필수 |
| 성공 지표(KPI) | 측정 가능한 수치. AI 제품은 recall/precision 등 명확한 지표+임계치 | 필수 |
| No-go (Out-of-Scope) | 뺀 항목 + 왜 뺐는지 이유 | 필수 |
| User Story | "왜냐하면" 근거까지 포함, 1~3개 페르소나 | 필수 |
| Design/시각자료 | 임베드·링크로 통합 | 상황에 따라 선택 |

**섹션별 깊이 배분 원칙**: 모든 섹션을 균등한 깊이로 쓰지 않는다 — 핵심 섹션(문제 정의, 솔루션)에 더 많은 시간과 분량을 쓰고, 부차적 섹션은 상황에 따라 가볍게 쓰거나 생략한다.

## 7️⃣ 문서 분량/구조 기준 — 장황함 방지

### 정량 기준

리뷰했던 실제 PRD의 섹션별 분량 실측 결과, **"핵심 제품 서사"(문제-가설-목표-범위)가 전체의 15%뿐이고 나머지 85%가 실행/검증/리스크 완화 절차였다.** 이 비율이 뒤집혀야 한다 — 제품 서사가 문서의 주(主), 실행 디테일은 종(從)이어야 한다.

### 중복 제거 원칙

같은 정보를 여러 곳에 반복 서술하지 않는다. (실제 사례: Payroll 응답 처리 로직이 세 곳에 반복되어 있었고, 이 때문에 나중에 결정을 재검토할 때 여러 곳을 동시에 고쳐야 하는 문제가 실제로 발생함.)

### 이관 항목 명시화

ERD로 옮기는 항목은 삭제가 아니라, "무엇을 어디로 옮길지" 목록으로 PRD에 남겨 추적 가능하게 한다.

```
| 이관 대상 | 이관처 | 이유 |
| Case 3.2.2.x 중첩 분기 로직 | Router 설계 문서 | 사용자가 인지 못 하는 내부 상태 전이 = How |
| 골든셋 라벨 스키마 | 평가 계획서 | "90%를 어떻게 측정하는가" = How |
```

## 8️⃣ 리스크(Rabbit holes) 작성 기준

| 원칙 | 이유 |
| --- | --- |
| 리스크명 + 오너 + 기한 필수 | 오너·기한 없으면 "적어만 놓고 방치"되는 리스크가 됨 |
| 완화책은 "무엇을 할지"까지만 | 완화책 자체가 감사 절차·모니터링 주기까지 상세화되면 미니 운영 매뉴얼이 되어 다시 How로 흐름 |

```
| # | 리스크 | 오너 | 기한 |
| R1 | Task Card 중복 생성 | PM + Eng | 파일럿 전(9월) |
```

## ✅ 종합 체크리스트 (다음 PRD 작성 전 자가 점검)

- [ ] 문제를 해결책보다 먼저 썼는가? 정량 근거가 있는가?
- [ ] 성공 지표에 구체적 수치가 있는가? (AI 제품이면 recall/precision 중 무엇을 쓸지, accuracy를 쓰면 안 되는 이유를 아는가?)
- [ ] No-go 항목마다 "왜 뺐는지"가 붙어있는가?
- [ ] 컴포넌트 이름 중 "이 PRD가 새로 발명한 내부 구조"가 있다면 순화했는가?
- [ ] timeout/API/로직/kill switch 같은 순수 기술 용어를 평이한 말로 바꿨는가?
- [ ] Acceptance Criteria 중 조건부 규칙은 G/W/T로, 불변식·지표 게이트는 서술로 구분했는가?
- [ ] 같은 정보가 여러 섹션에 중복되어 있지 않은가?
- [ ] ERD로 옮길 항목이 "이관 목록"으로 추적 가능하게 남아있는가?
- [ ] 리스크마다 오너와 기한이 있는가?
- [ ] 문서 전체에서 "제품 서사" 분량이 "실행 디테일" 분량보다 우세한가?
