## 1. 용어집

| 용어                          | 뜻                                                                                |
| ----------------------------- | --------------------------------------------------------------------------------- |
| **core**                      | CPU 코어 1개 분량의 처리 시간입니다. 0.5 core는 코어 1개를 절반만큼 쓰는 양입니다 |
| **m (millicore)**             | 1/1000 core입니다. `100m` = 0.1 core, `500m` = 0.5 core                           |
| **Mi (mebibyte)**             | 1024 × 1024 byte입니다. `256Mi` ≈ 268 MB                                          |
| **request**                   | 파드에 보장되는 자원 예약량입니다. 노드 배치의 기준이 됩니다                      |
| **limit**                     | 파드가 쓸 수 있는 자원의 최대치입니다                                             |
| **scheduler**                 | 새 파드를 어느 노드에 올릴지 정하는 Kubernetes 구성 요소입니다                    |
| **allocatable (할당 가능량)** | 노드 전체 용량에서 OS·kubelet 몫을 뺀, 파드에 나눠 줄 수 있는 양입니다            |
| **throttling**                | CPU 사용량이 limit에 닿아 커널이 파드 실행을 강제로 멈추게 하는 현상입니다        |
| **CPU 경합 (contention)**     | 노드가 붐벼서 request를 넘는 몫을 다른 파드와 나눠 써야 하는 상황입니다           |
| **OOMKilled**                 | 메모리가 limit을 넘어서 컨테이너가 강제 종료된 상태입니다(OOM = Out Of Memory)    |
| **eviction (축출)**           | 노드 자원이 부족할 때 kubelet이 파드를 내쫓는 동작입니다                          |
| **Pending**                   | 파드가 생성되었지만 들어갈 노드를 찾지 못해 대기 중인 상태입니다                  |
| **overcommit**                | 설정값의 합계가 실제 물리 용량을 넘도록 허용하는 것입니다                         |
| **replica**                   | 같은 Deployment에서 띄운 동일한 파드의 개수입니다                                 |
| **rolling update**            | 새 버전 파드를 먼저 띄우고 옛 파드를 차례로 내리는 기본 배포 방식입니다           |

## 2. 이 문서가 필요한 이유: SigNoz 파드 목록 화면

SigNoz(관측 도구)의 Kubernetes 인프라 화면에서 파드 목록을 열면 다음과 같은 컬럼이 나옵니다.

```
Pod Name | CPU Req Usage (%) | CPU Limit Usage (%) | CPU Usage (cores) | Mem Req Usage (%) | Mem Limit Usage (%) | Mem Usage
```

예를 들어 tax-agent 파드 한 줄은 다음과 같았습니다.

| Pod Name                          | CPU Req | CPU Limit | CPU Usage | Mem Req | Mem Limit | Mem Usage |
| --------------------------------- | ------- | --------- | --------- | ------- | --------- | --------- |
| tax-agent-engine-7dcccb58d5-5m7pg | 12%     | 2%        | 0.01      | 42%     | 21%       | 107.45 MB |

같은 CPU인데 12%, 2%, 0.01이라는 세 숫자가 동시에 나오기 때문에 처음 보면 무엇을 기준으로 판단해야 할지 헷갈립니다. 이 숫자들을 이해하려면 먼저 request와 limit이라는 두 기준값을 알아야 합니다.

## 3. 기준값 두 가지: request와 limit

### 3.1 manifest에 적는 값

request와 limit은 Deployment manifest의 컨테이너 설정에 적습니다. tax-agent의 세 앱(engine·orchestrator·payroll-relay)은 모두 같은 값을 쓰고 있습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tax-agent-engine
spec:
  replicas: 3
  selector:
    matchLabels:
      app: tax-agent-engine
  template:
    metadata:
      labels:
        app: tax-agent-engine
    spec:
      containers:
        - name: app
          image: example/tax-agent-engine:latest
          resources:
            requests:
              cpu: 100m      # 0.1 core 보장
              memory: 256Mi  # 256Mi 보장
            limits:
              cpu: 500m      # 0.5 core 상한
              memory: 512Mi  # 512Mi 상한
```

(위 manifest에서 `resources` 부분은 실제 설정값이고, `replicas`·`image` 등은 예시입니다.)

### 3.2 두 값의 위치

```
  0 ─────────── request ─────────────── limit ──────▶ 자원량
                (100m / 256Mi)          (500m / 512Mi)
                 │                       │
                 │                       └─ 상한선. 넘으면:
                 │                           CPU → throttling(실행 지연)
                 │                           메모리 → OOMKilled(파드 강제 종료)
                 └─ 예약량. scheduler가 노드를 고를 때 이만큼 자리가 있는지 본다
```

- **request**: 파드에 보장되는 예약량입니다. 노드 배치는 이 값을 기준으로 결정됩니다. 실제로 그만큼 쓰고 있다는 뜻은 아닙니다. 쓰든 안 쓰든 노드에서 그만큼 자리를 잡아 둡니다.
- **limit**: 파드가 쓸 수 있는 최대치입니다.

### 3.3 request와 limit의 성격 비교

| 구분                 | request                                                          | limit                                             |
| -------------------- | ---------------------------------------------------------------- | ------------------------------------------------- |
| 의미                 | "이만큼은 보장해 줘"                                             | "아무리 많아도 이 이상은 쓰지 마"                 |
| 노드 용량과의 관계   | 노드에 올라간 파드들의 합계가 할당 가능량을 **넘을 수 없습니다** | 합계가 노드 용량을 **넘어도 됩니다** (overcommit) |
| scheduler가 보나     | 봅니다 (배치 기준)                                               | **보지 않습니다**                                 |
| 초과했을 때 (CPU)    | 노드가 붐비면 경합으로 덜 받을 수 있습니다                       | throttling이 걸립니다                             |
| 초과했을 때 (메모리) | 노드 메모리가 부족하면 먼저 축출 대상이 됩니다                   | OOMKilled로 재시작됩니다                          |

비유하면 request는 **지정 좌석 예매**라서 좌석 수 이상 팔 수 없고, limit은 **"1인당 최대 몇 접시까지"라는 뷔페 규칙**이라서 모든 손님이 동시에 최대치를 먹는 상황을 처음부터 가정하지 않습니다. limit은 7절에서 자세히 다룹니다.

### 3.4 참고: request·limit 조합에 따른 QoS 등급

Kubernetes는 request와 limit을 어떻게 설정했는지에 따라 파드에 QoS(Quality of Service) 등급을 붙이고, 노드 자원이 부족할 때 축출 순서를 정하는 데 사용합니다.

| QoS 등급   | 조건                                            | 축출 우선순위          |
| ---------- | ----------------------------------------------- | ---------------------- |
| Guaranteed | 모든 컨테이너에서 CPU·메모리의 request = limit  | 가장 나중에 축출됩니다 |
| Burstable  | request가 하나라도 있고, Guaranteed 조건은 아님 | 중간입니다             |
| BestEffort | request·limit이 하나도 없음                     | 가장 먼저 축출됩니다   |

tax-agent 파드는 request(100m/256Mi)와 limit(500m/512Mi)이 다르므로 **Burstable**에 해당합니다.

## 4. SigNoz 파드 목록의 컬럼 6개

### 4.1 컬럼별 의미

화면의 퍼센트 컬럼 네 개는 실제 사용량을 request나 limit으로 나눈 값입니다. 실제로 측정한 값은 `CPU Usage (cores)`와 `Mem Usage` 두 개뿐입니다. **세 값 모두 노드 전체가 아니라 그 파드 하나 기준입니다.**

| 컬럼                    | 계산식                     | tax-agent 파드의 분모 | 해석                                                                            |
| ----------------------- | -------------------------- | --------------------- | ------------------------------------------------------------------------------- |
| **CPU Usage (cores)**   | 실제 CPU 사용량            | –                     | 원본 값입니다. 0.01은 10m에 해당합니다                                          |
| **CPU Req Usage (%)**   | CPU Usage ÷ CPU request    | 0.1 core              | 예약해 둔 CPU 중 실제로 쓰는 비율입니다                                         |
| **CPU Limit Usage (%)** | CPU Usage ÷ CPU limit      | 0.5 core              | 100%에 가까워지면 throttling이 걸립니다                                         |
| **Mem Usage**           | 실제 메모리 사용량         | –                     | 원본 값입니다                                                                   |
| **Mem Req Usage (%)**   | Mem Usage ÷ memory request | 256Mi                 | 100%를 넘을 수 있습니다. 넘으면 노드 메모리가 부족할 때 먼저 축출 대상이 됩니다 |
| **Mem Limit Usage (%)** | Mem Usage ÷ memory limit   | 512Mi                 | 100%에 도달하면 OOMKilled로 파드가 재시작됩니다                                 |

```
┌──────────────── Node (예: 2 core) ────────────────┐
│                                                   │
│  ┌─ engine 파드 ─┐  ┌─ orchestrator 파드 ─┐  ...  │
│  │ request 0.1   │  │ request 0.1         │       │
│  │ limit   0.5   │  │ limit   0.5         │       │
│  │ usage 0.012 ◀─┼──┼── 화면의 한 행은 이 파드 하나의 값
│  └───────────────┘  └─────────────────────┘       │
└───────────────────────────────────────────────────┘
```

### 4.2 검산: 실제 행에 계산식 대입하기

`tax-agent-engine-7dcccb58d5-5m7pg`의 값을 계산식에 넣으면 화면의 숫자와 맞아떨어집니다.

| 컬럼      | 계산                  | 화면 값 |
| --------- | --------------------- | ------- |
| CPU Req   | 약 0.012 ÷ 0.1 = 12%  | 12% ✅  |
| CPU Limit | 약 0.012 ÷ 0.5 ≈ 2.4% | 2% ✅   |
| Mem Req   | 107.45 ÷ 256 ≈ 42%    | 42% ✅  |
| Mem Limit | 107.45 ÷ 512 ≈ 21%    | 21% ✅  |

두 가지를 알 수 있습니다.

- CPU Usage는 0.01로 표시되지만 퍼센트 값에서 거꾸로 계산하면 약 0.012 core입니다. 화면에 표시할 때 반올림된 것으로 보입니다.
- 107.45 ÷ 256이 42%가 되려면, 화면의 "MB" 단위가 사실상 MiB여야 합니다.

### 4.3 이 화면 전체를 읽은 결과

- **CPU**: 모든 파드가 request의 12% 이하를 쓰고 있습니다. 조회 시점만 보면 CPU는 넉넉합니다. 다만 이 값은 조회 구간의 평균일 가능성이 높으므로, 순간적인 부하는 10절의 방법으로 따로 확인해야 합니다.
- **메모리**: limit 대비 약 16~24%로 여유가 있습니다.
- **용도 구분**: Req Usage 컬럼은 request를 너무 크거나 작게 잡았는지 판단할 때(rightsizing), Limit Usage 컬럼은 장애 위험을 판단할 때 씁니다.

## 5. CPU 세 컬럼의 차이: 실제 값 하나, 기준선 둘

### 5.1 핵심

세 컬럼은 서로 다른 것을 재는 값이 아닙니다. **실제로 쓴 양은 `CPU Usage (cores)` 하나뿐이고**, 나머지 두 컬럼은 그 양을 서로 다른 기준선에 대어 본 비율입니다. 같은 키를 "평균 키 대비 몇 %", "문 높이 대비 몇 %"로 다시 표현한 것과 같습니다.

### 5.2 비유: 회사 회의실 예약

파드를 회의실을 쓰는 팀이라고 생각해 보겠습니다.

| 개념          | 회의실 비유                                                    | tax-agent 파드의 값 |
| ------------- | -------------------------------------------------------------- | ------------------- |
| **request**   | "우리 팀 자리 **10석**은 꼭 확보해 주세요" (예약석)            | 0.1 core            |
| **limit**     | "아무리 붐벼도 **50석**까지만 쓸 수 있습니다" (최대 수용 인원) | 0.5 core            |
| **CPU Usage** | 지금 실제로 앉아 있는 인원                                     | 0.012 core          |

지금 실제로 **1.2명**이 앉아 있다면 다음과 같이 계산됩니다.

```
실제 인원(CPU Usage) = 1.2명  ← 측정한 값은 이것 하나뿐

예약석 대비   → 1.2 ÷ 10 = 12%   (CPU Req Usage)
최대 인원 대비 → 1.2 ÷ 50 = 2.4%  (CPU Limit Usage)
```

### 5.3 그림으로 보기

```
CPU (core)
0        0.012         0.1                          0.5
├──────────●────────────┤────────────────────────────┤
           │            │                            │
     실제 사용량      request                       limit
   (CPU Usage)       (예약량)                      (상한선)

   ●까지의 길이 ÷ request까지의 길이 = 12%   → CPU Req Usage
   ●까지의 길이 ÷ limit까지의 길이   = 2.4%  → CPU Limit Usage
```

tax-agent 파드는 limit이 request의 5배이므로, **같은 순간에 Req Usage는 항상 Limit Usage의 5배**입니다.

### 5.4 왜 같은 값을 두 번 나눠서 보여 주는가

두 비율은 각각 다른 질문에 답합니다.

| 컬럼                | 답하는 질문             | 높을 때                                                                                  | 낮을 때                                                                           |
| ------------------- | ----------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **CPU Req Usage**   | 예약을 적당히 잡았나?   | 100%를 넘으면 예약보다 많이 쓰는 중입니다. 노드가 붐비면 보장받지 못하는 부분이 생깁니다 | 예약석을 비워 두는 셈입니다. 다른 파드가 그 자리를 쓸 수 없어서 노드가 낭비됩니다 |
| **CPU Limit Usage** | 상한선에 부딪히고 있나? | 100%에 가까우면 throttling이 걸려 응답이 느려집니다                                      | 상한까지 여유가 있습니다                                                          |

## 6. 사용량 구간별로 일어나는 일: 보장·경합·throttling

### 6.1 세 구간

Req Usage 100%와 Limit Usage 100%는 같은 "100%"이지만 분모가 다르기 때문에, **실제 CPU 양으로 바꾸면 서로 다른 지점**입니다. tax-agent 파드 기준으로 Req 100%는 0.1 core를 쓸 때, Limit 100%는 0.5 core를 쓸 때입니다.

```
CPU 사용량 (core)
0          0.1                                   0.5
├───────────┼─────────────────────────────────────┤
│ ① 보장 구간 │        ② 경합 가능 구간              │ ③ throttling
│           │                                     │
│      Req 100%                              Limit 100%
│     (=Limit 20%)                          (=Req 500%)
```

| 구간             | 사용량       | 무슨 일이 일어나나                                                                                   |
| ---------------- | ------------ | ---------------------------------------------------------------------------------------------------- |
| ① 0 ~ 0.1 core   | Req 0~100%   | **보장된 몫**입니다. 노드가 붐벼도 이만큼은 받습니다                                                 |
| ② 0.1 ~ 0.5 core | Req 100~500% | **노드에 남는 CPU가 있으면** 더 쓸 수 있습니다. 다른 파드도 바빠지면 경합이 생겨 덜 받을 수 있습니다 |
| ③ 0.5 core       | Limit 100%   | **노드가 한가해도** 더는 쓸 수 없습니다. 강제로 실행이 멈칫거립니다(throttling)                      |

정리하면 다음과 같습니다.

- **Req 100%를 넘는 것**: "이제부터는 보장이 아니라 남는 CPU를 빌려 쓰는 중"이라는 신호입니다. 노드가 한가하면 아무 문제가 없습니다. **Req Usage가 100%를 넘는 것 자체는 장애가 아닙니다.**
- **Limit 100%에 닿는 것**: "노드 사정과 상관없이 천장에 닿았다"는 신호입니다. 이때부터는 처리가 확실히 느려집니다.

### 6.2 "request 안에서는 보장된다"의 전제

request까지 보장된다는 말이 성립하려면 **노드에 올라간 파드들의 request 합계가 노드의 할당 가능량을 넘지 않아야** 합니다. scheduler가 파드를 배치할 때 이 조건을 지키기 때문에 평소에는 이 전제가 유지됩니다.

### 6.3 노드가 붐빌 때 CPU를 나누는 방식

노드의 CPU가 부족하면 Kubernetes(정확히는 리눅스 커널의 CPU 스케줄러)는 남는 CPU를 **각 파드의 request 크기에 비례해서** 나눠 줍니다. 그래서 request가 작은 파드일수록 붐빌 때 덜 받습니다.

### 6.4 경합과 throttling은 다른 현상이다

request를 넘었을 때 다른 파드와 경쟁해서 CPU를 덜 받는 현상은 throttling이라고 부르지 않고 **CPU 경합(contention)**이라고 부릅니다. Kubernetes에서 throttling은 **limit에 닿아서 강제로 멈추는 현상**만 가리킵니다.

| 구분          | ② CPU 경합 (contention)                                                      | ③ Throttling                                                                                                                    |
| ------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 언제 생기나   | request를 넘게 쓰는데 **노드가 붐빌 때**                                     | **limit에 닿았을 때** (노드가 한가해도)                                                                                         |
| 원인          | 남는 CPU를 다른 파드와 나눠 써야 해서                                        | 설정된 상한선 때문에                                                                                                            |
| 결과          | 원하는 만큼 못 받아서 느려집니다                                             | 상한까지만 쓰고 강제로 대기합니다                                                                                               |
| 어디서 보이나 | 파드 지표만으로는 잘 보이지 않습니다. **노드 CPU 사용률**을 함께 봐야 합니다 | throttling 지표에 직접 찍힙니다 (cAdvisor 기준 `container_cpu_cfs_throttled_periods_total`, SigNoz에서의 지표 이름은 확인 필요) |
| 대응          | request를 올리거나, 붐비는 노드를 피하도록 배치를 조정합니다                 | limit을 올립니다                                                                                                                |

이 구분이 중요한 이유는 **대응 방법이 다르기 때문**입니다. 예를 들어 "파드가 느리다"는 신고를 받았는데 throttling 지표가 0이라면, limit을 올려도 아무것도 나아지지 않습니다. 이때는 노드 CPU가 꽉 차 있는지부터 확인해야 합니다.

### 6.5 상황별 예시

노드가 2 core이고 tax-agent 파드(request 0.1, limit 0.5)가 바빠진 경우입니다.

| 상황              | 파드가 원하는 양 | 실제로 받는 양                 | Req Usage | Limit Usage | 결과                                                         |
| ----------------- | ---------------- | ------------------------------ | --------- | ----------- | ------------------------------------------------------------ |
| A. 평소 (화면 값) | 0.012 core       | 0.012 core                     | 12%       | 2.4%        | 한가합니다. 예약도 상한도 넉넉합니다                         |
| B. 노드 한가함    | 0.3 core         | 0.3 core                       | 300%      | 60%         | 문제없습니다. 남는 CPU를 빌려 씁니다                         |
| C. 노드 붐빔      | 0.3 core         | 0.1 core 근처까지 밀릴 수 있음 | 약 100%   | 약 20%      | **경합** 때문에 느려질 수 있습니다                           |
| D. 노드 한가함    | 0.8 core         | **0.5 core**                   | 500%      | 100%        | 노드에 자리가 있어도 limit 때문에 느려집니다(**throttling**) |

C처럼 Req Usage가 100% 근처인데도 느려지는 경우가 있습니다. 이때 원인은 limit이 아니라 같은 노드의 다른 파드와 CPU를 나눠 쓰는 경합입니다.

### 6.6 메모리는 구간 동작이 다르다

CPU는 나눠 쓸 수 있어서 모자라면 **느려질 뿐**이지만, 메모리는 이미 할당한 것을 빼앗아 나눠 줄 수 없어서 모자라면 **누군가 종료되어야 합니다**.

| 구간                      | CPU                           | 메모리                                    |
| ------------------------- | ----------------------------- | ----------------------------------------- |
| request 이하              | 보장                          | 보장                                      |
| request 초과 ~ limit 미만 | 노드가 붐비면 경합으로 느려짐 | 노드 메모리가 부족하면 **축출 후보**가 됨 |
| limit 도달                | throttling (느려짐)           | **OOMKilled** (컨테이너 재시작)           |

그래서 평소에는 메모리 쪽의 **Mem Limit Usage**를 가장 주의 깊게 봐야 합니다.

## 7. limit 제대로 이해하기: 노드를 나눈 몫이 아니다

### 7.1 흔한 오해

"노드가 2 core이고 파드가 2개면 limit은 각각 1 core인가?"라는 질문에 대한 답은 **아니다**입니다. limit은 노드 용량을 파드 수로 나눈 값이 아니라, **파드마다 따로 정해 두는 독립적인 상한선**입니다. 그래서 limit의 합계는 노드 용량을 넘어도 됩니다(overcommit). 이 점이 "합계가 노드 할당 가능량을 넘을 수 없는" request와 가장 크게 다릅니다.

### 7.2 예시: 2 core 노드에 파드 2개

```
노드 할당 가능 CPU: 2 core (설명을 단순하게 하려고 2로 둡니다)

         request   limit
파드 A    0.5      1.5
파드 B    0.5      1.5
─────────────────────────
합계      1.0 ✅    3.0  ← 노드 2 core를 넘지만 허용됩니다
```

이 상태에서 상황별로 각 파드가 받는 CPU는 다음과 같습니다.

| 상황                          | 파드 A 받는 양 | 파드 B 받는 양 | 설명                                                                                                                 |
| ----------------------------- | -------------- | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| A만 바쁨                      | **1.5**        | 거의 0         | A는 limit까지 씁니다. 노드가 2 core여도 1.5에서 멈춥니다(throttling)                                                 |
| 둘 다 조금 바쁨 (각 0.8 원함) | 0.8            | 0.8            | 합계 1.6 ≤ 2라서 둘 다 원하는 만큼 받습니다                                                                          |
| 둘 다 매우 바쁨 (각 1.5 원함) | **1.0**        | **1.0**        | 합계 3이 노드 2를 넘어서 경합이 생깁니다. request 비율(0.5:0.5 = 1:1)로 나눠 받으므로, 둘 다 limit 1.5에 못 미칩니다 |

마지막 줄이 핵심입니다. **limit은 "여기까지 쓸 수 있다는 보장"이 아니라 "여기 이상은 절대 못 쓴다는 천장"**입니다. 천장 아래에서 실제로 얼마나 받을지는 노드가 얼마나 붐비는지에 달려 있습니다.

### 7.3 request 비율이 다른 경우

request가 다르면 붐빌 때 받는 양도 달라집니다.

```
노드 2 core, 두 파드 모두 limit 2.0, 둘 다 최대로 바쁜 상황

         request   붐빌 때 받는 양
파드 A    0.3       2 × 0.3/(0.3+0.1) = 1.5
파드 B    0.1       2 × 0.1/(0.3+0.1) = 0.5
```

request는 배치 기준일 뿐 아니라, **붐빌 때의 몫을 정하는 가중치**이기도 합니다.

### 7.4 메모리 limit의 overcommit은 더 위험하다

메모리 limit 합계가 노드 용량을 크게 넘는 상태에서 여러 파드가 동시에 메모리를 많이 쓰면, 각 파드가 자기 limit에 닿지 않았더라도 노드 전체가 메모리 부족에 빠집니다. 그러면 kubelet이 파드를 축출하거나 커널이 OOM으로 프로세스를 종료합니다.

```
노드 메모리 4Gi

         request   limit   실제 사용
파드 A    1Gi      3Gi     2.5Gi   ← 자기 limit 3Gi 안쪽
파드 B    1Gi      3Gi     2.0Gi   ← 자기 limit 3Gi 안쪽
─────────────────────────────────
합계                       4.5Gi > 4Gi  → 노드 메모리 부족 → 축출 또는 OOM 발생
```

그래서 메모리는 request와 limit을 가깝게(또는 같게) 잡는 팀이 많습니다.

## 8. request를 올리면 생기는 일: 배치 실패(Pending)

### 8.1 다른 파드의 request는 자동으로 줄지 않는다

request를 올려도 **다른 파드의 request가 자동으로 줄어드는 일은 없습니다**. 대신 노드마다 "request 합계가 할당 가능량을 넘으면 안 된다"는 규칙이 있어서, 자리가 모자라면 **request를 올린 내 파드가 배치되지 못하고 Pending 상태로 대기**합니다. 이 상황을 풀려면 노드를 늘리거나, 결국 누군가 다른 파드의 request를 직접 줄여야 합니다.

### 8.2 예시: 2 core 노드 하나

노드의 할당 가능 CPU가 1.8 core라고 가정하겠습니다(나머지는 OS·kubelet 몫).

```
현재 상태 (request 합계 1.5 / 1.8)
┌──────────────────── 할당 가능 1.8 core ────────────────────┐
│ engine 0.1 │ orch 0.1 │ relay 0.1 │ 다른 팀 파드들 1.2 │ 빈자리 0.3 │
└────────────────────────────────────────────────────────────┘
```

| 바꾸려는 것              | 필요한 자리 | 결과                                                    |
| ------------------------ | ----------- | ------------------------------------------------------- |
| engine request 0.1 → 0.3 | +0.2        | 빈자리 0.3 안에 들어가므로 배치됩니다                   |
| engine request 0.1 → 0.5 | +0.4        | 빈자리 0.3을 넘으므로 **이 노드에는 올라가지 못합니다** |

두 번째 경우에 일어나는 일은 클러스터에 남은 자원에 따라 갈립니다.

```
request 0.5짜리 새 파드
   │
   ├─ 다른 노드에 0.5 자리가 있다 → 그 노드로 배치 ✅
   │
   └─ 어느 노드에도 자리가 없다
         ├─ 노드 자동 증설(Cluster Autoscaler, Karpenter 등)이 켜져 있다
         │     → 노드 추가 → 배치 (비용 증가 💰)
         └─ 꺼져 있다 → 파드가 Pending 상태로 계속 대기 ⏳
                         → 사람이 노드를 늘리거나 다른 파드 request를 줄여야 풀림
```

### 8.3 놓치기 쉬운 점 두 가지

1. **배포하는 동안 자리가 더 필요합니다.** rolling update는 새 파드를 먼저 띄우고 옛 파드를 내리는 방식이 기본입니다. 그래서 잠시 동안 옛 파드(0.1)와 새 파드(0.5)의 request가 동시에 자리를 차지합니다. 여유가 빠듯한 클러스터에서는 이 순간에 새 파드가 Pending에 걸려 배포가 멈출 수 있습니다.
2. **replica 수만큼 곱해집니다.** request는 파드 하나 기준이므로, 같은 앱이 5개 떠 있다면 0.1 → 0.3으로 올릴 때 늘어나는 양은 0.2 × 5 = 1.0 core입니다.

### 8.4 남은 자리 확인하기

request를 올리기 전에는 노드별 request 합계와 남은 할당량을 먼저 확인합니다.

```bash
# 노드별 request·limit 합계와 할당 가능량 대비 비율
kubectl describe node <노드 이름> | sed -n '/Allocated resources/,/Events/p'

# Pending 파드와 그 이유 확인
kubectl get pods -n <namespace> --field-selector=status.phase=Pending
kubectl describe pod <파드 이름> -n <namespace> | sed -n '/Events/,$p'
# 자리가 없으면 "0/3 nodes are available: 3 Insufficient cpu." 같은 이벤트가 남습니다
```

`describe node` 출력의 Allocated resources 부분은 다음과 같은 형태입니다.

```
Allocated resources:
  Resource           Requests      Limits
  --------           --------      ------
  cpu                1500m (83%)   4500m (250%)
  memory             2Gi (60%)     4Gi (120%)
```

이 예시에서 CPU limit 합계가 250%인 것은 7절에서 설명한 overcommit이 정상적으로 허용되고 있다는 뜻입니다. 반면 request는 100%를 넘을 수 없습니다.

## 9. Pending을 배포 전에 막을 수 있는가

### 9.1 manifest만으로는 검증할 수 없다

계산식 자체는 `내 request ≤ 노드의 남은 자리`라는 단순한 산수입니다. 하지만 계산에 필요한 숫자 대부분이 manifest(helm chart·kustomize) 안에 없고 **클러스터의 현재 상태**에 있습니다.

| 필요한 값                                                | 어디에 있나                         | manifest로 알 수 있나 |
| -------------------------------------------------------- | ----------------------------------- | --------------------- |
| 내 파드의 request                                        | 내 chart                            | ✅                    |
| 노드 개수·크기                                           | 클러스터 (자동 증설 시 수시로 바뀜) | ❌                    |
| 다른 팀 파드들의 request                                 | 다른 팀 chart·클러스터              | ❌                    |
| DaemonSet(노드마다 하나씩 뜨는 파드, 예: 로그 수집기) 몫 | 클러스터                            | ❌                    |
| 이 파드가 갈 수 있는 노드 제한(taint·affinity)           | 내 chart + 노드 설정                | 절반만                |

숫자를 다 모아도 함정이 두 가지 더 남습니다.

**① 조각남(fragmentation)**: 클러스터 전체 합계로는 자리가 있어도, 한 노드에 몰려 있지 않으면 배치되지 않습니다.

```
요청: request 0.5 파드 1개

노드 A  빈자리 0.3
노드 B  빈자리 0.3      합계 0.6 ≥ 0.5 → 산수로는 "들어간다"
                        실제로는 0.5짜리 빈자리를 가진 노드가 없어서 Pending
```

**② 시점 차이**: 검사한 직후 다른 팀이 먼저 배포하면 그 자리가 사라집니다. 검사 결과는 검사한 순간에만 유효합니다.

### 9.2 그래도 할 수 있는 검증들

| 방법                                                                        | 언제             | 무엇을 잡나                                                                                          | 한계                                                              |
| --------------------------------------------------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **정적 규칙 검사** (conftest·Kyverno CLI 같은 정책 검사 도구를 CI에서 실행) | PR 단계          | "request가 가장 큰 노드보다 크다"처럼 **어디에도 절대 들어갈 수 없는 값**, request > limit 같은 실수 | 남은 자리는 모릅니다                                              |
| **ResourceQuota** (namespace별 request 합계 상한)                           | apply 단계       | 합계 초과를 **Pending 대신 즉시 거절**로 바꿔 줍니다                                                 | 조각남은 잡지 못합니다                                            |
| **`kubectl apply --dry-run=server`**                                        | 배포 직전        | 문법 오류, ResourceQuota 위반                                                                        | **scheduler를 거치지 않으므로 Pending 여부는 알려 주지 않습니다** |
| **용량 시뮬레이션** (kubernetes-sigs의 `cluster-capacity` 도구 등)          | 배포 직전        | 현재 클러스터에 이 파드 spec이 몇 개 들어가는지 노드 단위로 계산                                     | 시점 차이 문제는 남습니다                                         |
| **남은 자리 조회** (`kubectl describe node`, `kube-capacity` 플러그인)      | 사람이 판단할 때 | 노드별 request 합계와 여유                                                                           | 수동입니다                                                        |

ResourceQuota 예시는 다음과 같습니다. 이 namespace의 모든 파드 request 합계가 CPU 2 core를 넘으면 apply 자체가 거절됩니다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: example-namespace
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "8"
    limits.memory: 8Gi
```

### 9.3 실무에서 더 흔한 방식: 막지 않고 빨리 알아채기

사전 검증이 완벽할 수 없기 때문에, 대부분의 팀은 아래 장치를 조합해서 위험을 줄입니다.

```
request 변경 PR
   │
   ├─ CI: 정적 규칙 검사 ── 가장 큰 노드보다 크면 PR 실패
   │
   ▼
ArgoCD 동기화
   │
   ├─ 노드 자동 증설(Cluster Autoscaler·Karpenter) ── 자리가 없으면 노드를 추가
   │
   └─ 그래도 Pending이면
        ├─ Deployment의 progressDeadlineSeconds 초과 → rollout 실패로 표시
        └─ ArgoCD 앱 상태가 Progressing/Degraded로 남음 → 알림
```

rolling update 덕분에 **새 파드가 Pending이어도 옛 파드는 계속 서비스합니다.** 그래서 Pending 자체가 곧바로 장애로 이어지지는 않고, "배포가 끝나지 않았다"는 신호로 받아들이고 대응할 수 있습니다.

`progressDeadlineSeconds`는 Deployment에 설정하며, 이 시간 안에 rollout이 진척되지 않으면 Deployment 상태에 실패 조건이 기록됩니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tax-agent-engine
spec:
  progressDeadlineSeconds: 600   # 10분 안에 진척이 없으면 rollout 실패로 표시 (기본값 600)
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 새 파드를 최대 1개 먼저 띄움 → 그만큼 request 자리가 추가로 필요
      maxUnavailable: 0    # 옛 파드는 새 파드가 준비된 뒤에만 내림
  # ... (selector, template 생략)
```

## 10. 실전: CPU 지표를 보수적으로 읽는 법

### 10.1 Req Usage가 더 보수적인 기준이다

"보장된 몫을 넘었는지"를 먼저 알아채는 용도로는 **Req Usage**가 더 보수적인 기준입니다. 같은 사용량에서 Req Usage가 항상 먼저 높게 나오기 때문입니다.

| 사용량    | Req Usage        | Limit Usage                   |
| --------- | ---------------- | ----------------------------- |
| 0.08 core | 80% ⚠️ 슬슬 주의 | 16% (아직 한참 여유처럼 보임) |
| 0.1 core  | 100%             | 20%                           |

Limit Usage만 보면 20%여서 안심하게 되지만, 실제로는 이미 보장 구간을 다 쓴 상태입니다. 그래서 **조기 경보** 역할은 Req Usage가 더 잘합니다.

### 10.2 그러나 Req Usage만으로는 부족하다

Req Usage가 높다는 것은 "위험해질 수 있는 구간에 들어섰다"는 뜻이지, "느려졌다"는 뜻은 아닙니다.

```
Req Usage 300%  +  노드 한가함  →  아무 문제 없음
Req Usage 300%  +  노드 붐빔    →  경합으로 느려짐
```

목적에 따라 함께 볼 지표가 달라집니다.

| 알고 싶은 것                      | 볼 지표                                             |
| --------------------------------- | --------------------------------------------------- |
| request를 적절히 잡았나 (사이징)  | **Req Usage**                                       |
| 경합으로 느려질 위험이 있나       | Req Usage **+ 노드 전체 CPU 사용률**                |
| throttling이 실제로 일어나고 있나 | Limit Usage **+ throttling 지표**                   |
| 메모리 때문에 죽을 위험이 있나    | **Mem Limit Usage** (+ 재시작 횟수, OOMKilled 이력) |

### 10.3 평균값의 함정

화면에 보이는 숫자는 조회 구간의 **평균**일 가능성이 높습니다(SigNoz의 집계 방식은 확인 필요). 평균은 순간적인 폭주를 지워 버립니다.

```
CPU
0.5 ┤      █                   ← 잠깐 limit에 닿아 throttling 발생
    │      █
0.1 ┤──────█───────────────── request
    │ ▁▁▁▁▁█▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁
    └──────────────────────▶ 시간
    평균을 내면 → 0.02 core (Req 20%, Limit 4%)  "아주 한가함"처럼 보임
```

특히 throttling은 **기본 100ms 단위로 할당량을 검사**합니다. limit 0.5 core는 "100ms마다 CPU 시간 50ms까지"라는 뜻입니다.

```
limit 0.5 core = 100ms 주기마다 CPU 시간 50ms 허용

스레드 4개가 동시에 일하는 경우:
  4 스레드 × 12.5ms = 50ms  → 주기가 시작되고 12.5ms 만에 할당량 소진
  남은 87.5ms 동안 4 스레드 모두 대기 (throttled)

1초 평균으로 보면 이런 순간이 드물어서 사용률은 낮게 나옵니다.
```

이처럼 평균 사용률이 낮아도, 여러 스레드가 짧게 몰려서 일하는 앱에서는 throttling이 일어날 수 있습니다. 예를 들어 요청이 들어올 때만 여러 스레드가 동시에 처리하는 앱은 평소에 한가해 보여도 처리하는 순간에는 천장에 닿을 수 있습니다.

### 10.4 보수적으로 보는 절차

1. **Req Usage를 기본 기준으로 봅니다.** 평소 값이 꾸준히 100%를 넘으면 request를 올릴지 검토합니다(올리기 전에 8절의 남은 자리 확인).
2. **평균이 아니라 최댓값이나 p95(상위 5% 값)로 봅니다.** SigNoz 시계열 그래프에서 집계 방식을 `max`로 바꿔 확인합니다.
3. **느리다는 신호가 있으면** throttling 지표와 노드 CPU 사용률을 함께 열어, 원인이 limit(throttling)인지 경합인지 구분합니다.
4. **메모리는 Mem Limit Usage를 따로 감시합니다.** CPU와 달리 초과하는 순간 파드가 재시작됩니다.

## 11. 정리

| 질문                                      | 답                                                                                                                                                            |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 실제로 측정한 값은?                       | `CPU Usage (cores)`와 `Mem Usage`뿐입니다. 둘 다 **파드 하나** 기준입니다                                                                                     |
| Req Usage는?                              | 실제 사용량 ÷ request. 예약을 적절히 잡았는지 판단할 때 씁니다                                                                                                |
| Limit Usage는?                            | 실제 사용량 ÷ limit. 천장에 닿을 위험을 판단할 때 씁니다                                                                                                      |
| Req 100% 초과는 장애인가?                 | 아닙니다. 보장 구간을 넘어 남는 CPU를 빌려 쓰는 중입니다. 노드가 붐비면 **경합**으로 느려질 수 있습니다                                                       |
| Limit 100%는?                             | 노드 사정과 상관없이 **throttling**(CPU) 또는 **OOMKilled**(메모리)가 발생합니다                                                                              |
| 경합과 throttling의 차이는?               | 경합은 노드가 붐벼서, throttling은 limit 때문에 느려지는 것입니다. 대응이 다릅니다(request 조정 또는 배치 조정 vs limit 조정)                                 |
| limit은 노드를 나눈 몫인가?               | 아닙니다. 파드별 독립 상한선이고, 합계가 노드 용량을 넘어도 됩니다(overcommit). scheduler는 limit을 보지 않습니다                                             |
| request를 올리면 다른 파드가 줄어드나?    | 자동으로 줄지 않습니다. 대신 자리가 없으면 내 파드가 Pending이 됩니다                                                                                         |
| Pending을 manifest 단계에서 막을 수 있나? | "어디에도 들어갈 수 없는 값"만 정적으로 걸러낼 수 있습니다. 나머지는 클러스터 상태가 필요해서, CI 정적 검사 + 노드 자동 증설 + rollout 실패 알림을 조합합니다 |
| 보수적으로 보려면?                        | Req Usage를 기본으로 보되, 평균이 아니라 최댓값으로 보고, 느리면 throttling 지표와 노드 CPU를 함께 봅니다                                                     |

### tax-agent 파드의 현재 설정과 상태 (조회 시점 기준)

- 설정: 세 앱 모두 request **CPU 100m · 메모리 256Mi**, limit **CPU 500m · 메모리 512Mi** (QoS 등급 Burstable)
- CPU: 모든 파드가 request의 12% 이하 (평균값 기준)
- 메모리: limit 대비 약 16~24%

### 확인하지 않은 사항

- SigNoz의 `Mem Usage`가 working set 기준인지 RSS 기준인지
- SigNoz 파드 목록 값의 시간 집계 방식(평균인지 여부)과 throttling 지표 이름
- 이 클러스터에 노드 자동 증설·ResourceQuota·ArgoCD 알림이 설정되어 있는지
