## 0. 용어 정리

| chunking                             | 긴 문서를 검색 단위의 조각(chunk)으로 자르는 작업                                    |

| text-to-SQL                          | 자연어 질문을 LLM이 SQL로 바꿔 실행하는 방식                                         |

## 1. 데이터 엔지니어란 무엇인가

데이터 엔지니어는 **데이터가 필요한 사람(분석가·데이터 사이언티스트·ML 모델·서비스)이 믿고 쓸 수 있도록, 데이터를 모으고 다듬어 제때 전달하는 시스템을 설계·구축·운영하는 사람**이다.

수도에 빗대면 데이터 엔지니어는 정수장과 배관을 만들고 관리하는 사람이고, 분석가와 데이터 사이언티스트는 그 물을 받아 쓰는 사람이다.

데이터 엔지니어의 핵심 질문은 하나로 모인다.

> "데이터가 정확하게, 제때, 효율적으로 필요한 곳에 도착하는가?"

## 2. 데이터가 흐르는 길과 핵심 업무

### 2.1 전체 그림

```
 [원천 데이터]           [데이터 엔지니어가 만드는 구간]                    [데이터를 쓰는 쪽]
                ┌──────────────────────────────────────────────┐
 서비스 DB ─────┤ ① 수집      ② 저장         ③ 변환          ├──▶ 분석가 (BI 대시보드)
 앱/웹 로그 ────┤ (Ingest) ─▶ (Lake/DW) ───▶ (정제·모델링) ──┼──▶ 데이터 사이언티스트
 외부 API ──────┤                                              ├──▶ ML 모델 학습/서빙
 IoT 센서 ──────┤ ④ 오케스트레이션 (언제·어떤 순서로 돌릴지)  ├──▶ 서비스 기능 (추천 등)
                │ ⑤ 품질·모니터링·거버넌스 (전 구간에 걸침)  │
                └──────────────────────────────────────────────┘
```

이 그림에서 **파이프라인(pipeline)**은 ①부터 ③까지 이어지는 흐름 전체를 말한다. ④와 ⑤는 그 파이프라인이 제때, 올바르게 돌도록 감싸는 층이다.

### 2.2 핵심 업무 5가지

| #   | 업무                      | 하는 일                                            | 예시                                                                      |
| --- | ------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------- |
| ①   | **수집 (Ingestion)**      | 여러 원천의 데이터를 한곳으로 가져옴               | 주문 DB 변경분을 CDC로 Kafka에 흘려보냄                                   |
| ②   | **저장 설계**             | 데이터를 어디에, 어떤 형식으로 둘지 결정           | 원본은 S3 Data Lake에 Parquet로, 분석용은 Snowflake/BigQuery DW에         |
| ③   | **변환 (Transformation)** | 정제·조인·집계해서 쓰기 좋은 테이블로 만듦         | 중복 제거, 타임존 통일, `daily_sales` 집계 테이블 생성 (dbt, Spark)       |
| ④   | **오케스트레이션**        | 작업 순서·스케줄·의존 관계·재시도 관리             | Airflow DAG: "매일 새벽 2시, 수집이 끝나면 변환 시작, 실패하면 3회 retry" |
| ⑤   | **품질·운영·거버넌스**    | 데이터가 맞는지 검증하고, 장애 대응·권한·비용 관리 | NULL 비율 급증 알림, 개인정보 컬럼 마스킹, 쿼리 비용 최적화               |

> **Parquet**: 열(column) 단위로 압축 저장하는 파일 형식. 분석 쿼리가 필요한 열만 읽을 수 있어 빠르고 저렴하다.

### 2.3 ETL vs ELT, Batch vs Streaming

**ETL과 ELT: 변환을 어디서 하는가**

```
 ETL:  원천 ──Extract──▶ 별도 변환 서버 ──Transform──▶ ──Load──▶ DW
                         (적재 전에 가공)

 ELT:  원천 ──Extract──▶ ──Load──▶ DW (원본 그대로 적재) ──Transform (DW 안에서 SQL로)──▶ 분석용 테이블
```

| 구분      | ETL                              | ELT                                                |
| --------- | -------------------------------- | -------------------------------------------------- |
| 순서      | 변환 → 적재                      | 적재 → 변환                                        |
| 배경      | 저장소가 비싸던 시절의 전통 방식 | 클라우드 DW가 싸고 강력해지면서 주류가 됨          |
| 장점      | DW에 깨끗한 데이터만 들어감      | 원본이 남아 있어 변환 로직을 바꿔 다시 돌리기 쉬움 |
| 대표 도구 | Informatica, 자체 Spark 작업     | Fivetran/Airbyte(수집) + dbt(변환)                 |

**Batch와 Streaming: 얼마나 자주 처리하는가**

| 구분 | Batch                                   | Streaming                   |
| ---- | --------------------------------------- | --------------------------- |
| 방식 | 정해진 주기(매시간, 매일)로 모아서 처리 | 데이터가 들어오는 즉시 처리 |
| 예   | 일일 매출 리포트                        | 실시간 이상거래 탐지        |
| 도구 | Spark, dbt, Airflow                     | Kafka, Flink                |
| 지연 | 분~시간 단위                            | 초 단위 이하                |

### 2.4 오케스트레이션과 품질 관리 예제

**오케스트레이션: Airflow DAG**

"매일 새벽 2시, 수집이 끝나면 변환을 시작하고, 실패하면 3회 retry"를 코드로 쓰면 다음과 같다. (Airflow 2.x 문법 기준이다. Airflow 3에서는 일부 import 경로가 바뀌었을 수 있다(확인 필요).)

```python
from datetime import datetime, timedelta

from airflow import DAG
from airflow.operators.bash import BashOperator

default_args = {
    "retries": 3,                          # 실패 시 3회 재시도
    "retry_delay": timedelta(minutes=10),  # 재시도 간격
}

with DAG(
    dag_id="daily_sales_pipeline",
    schedule="0 2 * * *",                  # 매일 02:00
    start_date=datetime(2026, 1, 1),
    catchup=False,                         # 과거 기간 자동 실행 안 함 (backfill은 수동으로)
    default_args=default_args,
) as dag:
    ingest_orders = BashOperator(
        task_id="ingest_orders",
        bash_command="python ingest_orders.py --date {{ ds }}",
    )
    ingest_ads = BashOperator(
        task_id="ingest_ads",
        bash_command="python ingest_ads.py --date {{ ds }}",
    )
    transform = BashOperator(
        task_id="dbt_run",
        bash_command="dbt run --select daily_sales",
    )

    # 두 수집 작업이 모두 끝나야 변환 시작
    [ingest_orders, ingest_ads] >> transform
```

- `{{ ds }}`는 Airflow가 실행 날짜(예: `2026-11-24`)로 채워 주는 템플릿 변수다. 날짜를 인자로 받게 만들어 두면 특정 날짜만 다시 돌리는 backfill이 쉬워진다.
- 실패 사례: 광고 API가 응답하지 않아 `ingest_ads`가 3번 모두 실패하면 `dbt_run`은 실행되지 않는다. 불완전한 데이터로 집계 테이블이 만들어지는 것을 막는 것이 의존 관계를 거는 이유다.

**품질 관리: NULL 비율 검사 SQL**

```sql
-- 어제 적재된 주문 중 user_id가 비어 있는 비율
SELECT
    COUNT(*)                                          AS total_rows,
    COUNT(*) FILTER (WHERE user_id IS NULL)           AS null_user_rows,
    ROUND(100.0 * COUNT(*) FILTER (WHERE user_id IS NULL) / NULLIF(COUNT(*), 0), 2)
                                                      AS null_ratio_pct
FROM raw_orders
WHERE ordered_at >= CURRENT_DATE - INTERVAL '1 day'
  AND ordered_at <  CURRENT_DATE;
```

평소 0.1%이던 `null_ratio_pct`가 갑자기 30%가 되면 원천 시스템의 스키마나 로직이 바뀌었다는 신호다. 이런 검사를 파이프라인에 넣어 기준을 넘으면 알림을 보내는 것이 ⑤번 업무다.

## 3. 옆 직군과의 차이, 그리고 하루 업무

### 관계도

```
 데이터 엔지니어 ──(신뢰할 수 있는 테이블 제공)──▶ 데이터 분석가 ──(인사이트)──▶ 의사결정자
        │
        └──(학습용 피처·데이터셋 제공)──▶ 데이터 사이언티스트 / ML 엔지니어 ──▶ 모델
```

| 직군                | 핵심 질문                                              | 산출물                                        |
| ------------------- | ------------------------------------------------------ | --------------------------------------------- |
| **데이터 엔지니어** | "데이터가 정확하게, 제때, 효율적으로 도착하는가?"      | 파이프라인, 테이블, 데이터 플랫폼             |
| 데이터 분석가       | "이 데이터가 무엇을 말하는가?"                         | 대시보드, 리포트                              |
| 데이터 사이언티스트 | "이 데이터로 무엇을 예측하거나 설명할 수 있는가?"      | 모델, 실험 결과                               |
| Analytics Engineer  | "분석가가 바로 쓸 수 있는 모델링된 테이블은 무엇인가?" | dbt 모델 (데이터 엔지니어와 분석가 사이 역할) |

### 하루 업무 예시

1. **아침**: 밤사이 돈 Airflow 작업 중 실패한 것이 없는지 확인한다. 결제 로그 수집이 원천 API 스키마 변경으로 깨졌다면 고쳐서 backfill한다.
2. **오전**: 마케팅팀이 요청한 "채널별 유입→구매 전환" 테이블을 설계한다. 원천 테이블 3개를 조인하는 dbt 모델을 만든다.
3. **오후**: 비용이 급증한 Spark 작업의 파티셔닝을 손본다.
4. **틈틈이**: "이 숫자 왜 어제랑 달라요?"라는 질문을 받고 lineage를 추적한다.

실제로는 새 파이프라인을 만드는 일보다 **이미 있는 파이프라인을 운영하고 데이터 신뢰성을 지키는 일**의 비중이 큰 경우가 많다.

### 회사 규모에 따른 범위

- **스타트업**: 한 사람이 수집부터 대시보드까지 맡는 경우가 많다. 분석가 업무 일부도 겸한다.
- **대기업·빅테크**: 세분화돼 있다. 플랫폼(인프라·Spark/Kafka 클러스터 운영), 파이프라인(도메인별 데이터 구축), Analytics Engineer 등으로 나뉜다.

채용공고를 볼 때는 직함보다 **"플랫폼을 만드는 쪽인지, 그 위에서 데이터를 만드는 쪽인지"**를 먼저 확인하는 것이 좋다. 이 구분에 따라 요구 역량이 소프트웨어 엔지니어링 쪽(분산 시스템, 인프라)과 데이터 모델링·SQL 쪽으로 크게 갈린다.

## 4. DBA와의 차이

한 문장으로 줄이면 **DBA는 그릇을 지키고, 데이터 엔지니어는 그릇 사이로 물을 나른다.** DBA는 데이터베이스라는 저장소 한 곳이 안정적이고 빠르고 안전하게 돌아가도록 지키는 사람이고, 데이터 엔지니어는 여러 저장소 사이로 데이터를 옮기고 가공하는 흐름을 만드는 사람이다.

### 4.1 담당 구간 비교

```
                 ┌─────── DBA 담당 ───────┐
                 │                        │
 사용자 ──▶ 서비스 앱 ──▶ [운영 DB (OLTP)] │
                 │   MySQL / PostgreSQL / Oracle
                 │   - 장애·백업·복구      │
                 │   - 성능 튜닝·인덱스    │
                 │   - 권한·보안           │
                 └──────────┬─────────────┘
                            │ ① 데이터를 빼냄 (CDC, 덤프)
                ┌───────────▼───────── 데이터 엔지니어 담당 ─────────┐
                │ 수집 ──▶ Data Lake ──▶ 변환 ──▶ DW (OLAP) ──▶ 분석·ML │
                └─────────────────────────────────────────────────────┘
```

- 운영 DB는 OLTP 작업을 처리하므로 DBA의 주 무대다.
- DW는 OLAP 작업을 처리하므로 데이터 엔지니어의 주 무대다.
- ① 구간은 **두 직군이 만나는 경계**다. 데이터 엔지니어가 운영 DB에서 데이터를 빼갈 때 서비스에 부하를 주지 않도록 DBA와 협의한다. 흔한 방법은 읽기 전용 복제본(read replica)에서 추출하거나, 부하가 적은 CDC 방식을 쓰는 것이다.

### 4.2 항목별 차이

| 항목          | DBA                                                                             | 데이터 엔지니어                                              |
| ------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **핵심 질문** | "DB가 죽지 않고, 빠르고, 데이터가 유실되지 않는가?"                             | "데이터가 필요한 곳에 정확하게 제때 도착하는가?"             |
| **관점**      | 저장소 **하나**를 깊게 봄                                                       | 저장소 **여러 개**를 잇는 흐름을 넓게 봄                     |
| **주 대상**   | 운영 DB (OLTP)                                                                  | Data Lake, DW (OLAP), 스트리밍                               |
| **주요 업무** | 설치·구성, 백업/복구, replication, 인덱스·쿼리 튜닝, 계정·권한, 버전 업그레이드 | 파이프라인 구축, ETL/ELT, 스케줄링, 데이터 모델링, 품질 검증 |
| **장애 상황** | "주문 DB 응답이 5초 걸린다" → 락·슬로우 쿼리 분석                               | "어제 매출 집계가 비었다" → 어느 단계에서 끊겼는지 추적      |
| **고객**      | 서비스 개발자, 운영팀                                                           | 분석가, 데이터 사이언티스트, ML 엔지니어                     |
| **주 도구**   | 특정 DBMS 전문 지식, 모니터링 도구, 실행 계획 (EXPLAIN)                         | Spark, Kafka, Airflow, dbt, 클라우드 DW                      |
| **코딩 비중** | 낮은 편 (SQL·셸 스크립트 중심)                                                  | 높은 편 (Python·SQL, 소프트웨어 엔지니어링)                  |

> **replication**: 한 DB의 데이터를 다른 DB 서버로 계속 복제해 장애에 대비하거나 읽기 부하를 나누는 것.
> **EXPLAIN**: DB가 쿼리를 어떤 순서·방법으로 실행할지(실행 계획) 보여 주는 명령.

### 4.3 같은 SQL, 다른 목적

**DBA가 보는 SQL**: 이 쿼리가 운영 DB를 느리게 만들지 않는지 본다.

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
-- 결과가 Seq Scan(전체 테이블 스캔)이면 → user_id에 인덱스 추가
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

**데이터 엔지니어가 쓰는 SQL**: 원천 데이터를 분석용 테이블로 바꾼다.

```sql
-- dbt 모델: daily_sales
SELECT DATE(ordered_at) AS day, region, SUM(amount) AS revenue
FROM raw.orders
GROUP BY 1, 2;
```

둘 다 SQL을 잘해야 하지만 DBA는 **성능과 안정성**을 위해, 데이터 엔지니어는 **변환과 모델링**을 위해 쓴다.

### 4.4 경계가 흐려지는 추세

1. **클라우드 관리형 DB 확산**: AWS RDS나 Aurora 같은 서비스가 백업·패치·failover(장애 시 예비 서버로 자동 전환)를 자동으로 해 주면서 전통적인 DBA 업무가 줄었다. 그래서 DBA는 **DBRE (Database Reliability Engineer)**처럼 자동화와 인프라 코드 쪽으로 진화하는 경우가 많다.
2. **DW 운영은 데이터 엔지니어가 맡음**: Snowflake나 BigQuery의 비용·성능·권한 관리를 데이터 엔지니어가 직접 하는 경우가 많아, 데이터 엔지니어가 "분석 DB의 DBA" 역할을 겸하게 됐다.
3. **커리어 전환이 잦음**: DBA 출신은 SQL·실행 계획·DB 내부 구조 이해가 깊어서, 파이프라인 도구만 익히면 데이터 엔지니어로 옮겨가기 유리하다.

### 구분하는 판단 기준

헷갈릴 때는 **"그 사람이 책임지는 대상이 무엇인가"**를 보면 된다.
- **특정 DB 인스턴스의 가용성·성능**이면 DBA다.
- **데이터가 원천에서 소비자까지 가는 흐름의 정확성·적시성**이면 데이터 엔지니어다.

## 5. DW 모델링은 누가, 어떻게 하는가

요즘 대부분의 회사에서 **DW 모델링은 데이터 엔지니어(또는 Analytics Engineer)가 직접 하고, DBA는 보통 관여하지 않는다.** 다만 혼자 하는 것은 아니고, 협업 상대가 DBA가 아니라 **원천 시스템 담당자와 데이터 소비자**다.

### 5.1 DBA가 아니라 데이터 엔지니어가 하는 이유

DBA가 잘하는 모델링은 운영 DB용 정규화 모델이고, DW 모델링은 목적과 기법이 다르다.

| 구분      | 운영 DB 모델링 (DBA·백엔드 개발자 영역)                                  | DW 모델링 (데이터 엔지니어 영역)                                     |
| --------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 목적      | 쓰기를 정확하고 빠르게, 중복 없이                                        | 읽기·집계를 쉽고 빠르게                                              |
| 기법      | 정규화 (3NF): 중복을 없애려고 테이블을 잘게 쪼갬                         | 차원 모델링 (Dimensional Modeling): 일부러 중복을 허용해 조인을 줄임 |
| 대표 구조 | 테이블 수십~수백 개가 FK (Foreign Key, 다른 테이블을 가리키는 키)로 얽힘 | Star Schema: Fact 1개 + Dimension 여러 개                            |
| 설계 근거 | "서비스가 어떤 데이터를 저장하나"                                        | "분석가가 어떤 질문을 던지나"                                        |

DW 모델링의 출발점이 **"비즈니스가 무엇을 알고 싶은가"**라서, 그 요구를 직접 받는 데이터 팀이 설계하는 것이 자연스럽다. 차원 모델링은 Ralph Kimball이 정립한 방법론이 가장 널리 쓰여서 흔히 "Kimball 방법론"이라고 부른다.

### 5.2 정규화 모델과 Star Schema 비교

**운영 DB (정규화)**: 주문 한 건을 보려면 테이블 여러 개를 조인해야 한다.

```
users ── orders ── order_items ── products ── categories
                       │
                   payments ── payment_methods
```

**DW (Star Schema)**: 데이터 엔지니어가 위 테이블들을 변환해 아래처럼 다시 짠다. 가운데 Fact를 Dimension이 별 모양으로 둘러싸서 Star Schema라고 부른다.

```
                 dim_user (나이대, 가입 채널, 지역)
                      │
 dim_date ──── fact_order_items ──── dim_product (상품명, 카테고리, 브랜드)
 (요일, 월, 분기)  (수량, 금액, 할인액)
                      │
                 dim_payment (결제 수단)
```

- **Fact 테이블**: 측정값(금액, 수량)이 쌓이는 "사건" 기록이다. 행 수가 매우 많고 계속 늘어난다.
- **Dimension 테이블**: 사건을 자르는 기준(누가, 언제, 무엇을)이다. `products`와 `categories`를 미리 합쳐 두는 것처럼 일부러 비정규화한다.

**실행 가능한 예제 (PostgreSQL)**

```sql
-- Dimension: 날짜
CREATE TABLE dim_date (
    date_key   INT PRIMARY KEY,      -- 20260715 같은 형태
    full_date  DATE NOT NULL,
    day_name   TEXT NOT NULL,
    month      INT  NOT NULL,
    quarter    INT  NOT NULL
);

-- Dimension: 상품 (운영 DB의 products + categories를 합친 것)
CREATE TABLE dim_product (
    product_key  INT PRIMARY KEY,
    product_name TEXT NOT NULL,
    category     TEXT NOT NULL,
    brand        TEXT NOT NULL
);

-- Dimension: 사용자
CREATE TABLE dim_user (
    user_key       INT PRIMARY KEY,
    age_group      TEXT NOT NULL,
    signup_channel TEXT NOT NULL,
    region         TEXT NOT NULL
);

-- Fact: 주문 상품 (grain = 주문 1건 안의 상품 1개)
CREATE TABLE fact_order_items (
    order_id        BIGINT NOT NULL,
    date_key        INT    NOT NULL REFERENCES dim_date (date_key),
    product_key     INT    NOT NULL REFERENCES dim_product (product_key),
    user_key        INT    NOT NULL REFERENCES dim_user (user_key),
    quantity        INT    NOT NULL,
    amount          NUMERIC(12, 2) NOT NULL,
    discount_amount NUMERIC(12, 2) NOT NULL DEFAULT 0
);

INSERT INTO dim_date VALUES
    (20260715, '2026-07-15', 'Wednesday', 7, 3),
    (20260820, '2026-08-20', 'Thursday',  8, 3),
    (20261005, '2026-10-05', 'Monday',   10, 4);

INSERT INTO dim_product VALUES
    (1, '무선 이어폰', '전자기기', 'BrandA'),
    (2, '러닝화',      '스포츠',   'BrandB');

INSERT INTO dim_user VALUES
    (100, '20대', '광고', '서울'),
    (200, '30대', '검색', '부산');

INSERT INTO fact_order_items VALUES
    (1, 20260715, 1, 100, 2, 30000, 1000),
    (2, 20260820, 2, 100, 1, 89000,    0),
    (3, 20260820, 1, 200, 1, 15000,    0),
    (4, 20261005, 2, 200, 1, 89000, 5000);

-- 분석가가 쓰는 쿼리: 분기·카테고리·지역별 매출
SELECT d.quarter, p.category, u.region, SUM(f.amount) AS revenue
FROM fact_order_items f
JOIN dim_date    d ON f.date_key    = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_user    u ON f.user_key    = u.user_key
GROUP BY 1, 2, 3
ORDER BY 1, 2, 3;
```

결과:

| quarter | category | region | revenue |
| ------- | -------- | ------ | ------- |
| 3       | 스포츠   | 서울   | 89000   |
| 3       | 전자기기 | 부산   | 15000   |
| 3       | 전자기기 | 서울   | 30000   |
| 4       | 스포츠   | 부산   | 89000   |

정규화된 운영 DB에서 같은 결과를 얻으려면 `orders`, `order_items`, `products`, `categories`, `users`를 모두 조인하고 날짜에서 분기를 계산해야 한다. Star Schema는 이 작업을 **미리 한 번** 해 두어 분석가가 매번 하지 않게 만든다.

### 5.3 grain과 SCD

**grain: 한 행이 무엇을 뜻하는가**

Fact 테이블을 설계할 때 가장 먼저 정하는 것이 grain이다. 위 예제의 `fact_order_items`는 grain이 "주문 1건 안의 상품 1개"다.

| grain 선택           | 장점                        | 실패 사례                                                                      |
| -------------------- | --------------------------- | ------------------------------------------------------------------------------ |
| 주문 상품 1개 (세밀) | 상품별·카테고리별 분석 가능 | 행이 많아짐                                                                    |
| 주문 1건 (거친)      | 행이 적고 단순              | "카테고리별 매출"을 물으면 답할 수 없음. 한 주문에 여러 카테고리가 섞이기 때문 |

grain을 정하려면 "분석가가 어떤 질문을 던지나"를 알아야 한다. 이것이 DW 모델링에서 데이터 소비자와 협업해야 하는 이유다.

**SCD: 바뀌는 속성을 어떻게 기록하나**

사용자가 서울에서 부산으로 이사했다고 하자. `dim_user.region`을 어떻게 바꾸느냐에 따라 과거 매출 분석 결과가 달라진다.

| 방식       | 동작                                    | 결과                                                       |
| ---------- | --------------------------------------- | ---------------------------------------------------------- |
| SCD Type 1 | 기존 값을 덮어씀                        | 과거 서울 시절 매출까지 전부 "부산 매출"로 집계됨          |
| SCD Type 2 | 기존 행을 닫고 새 행을 추가 (이력 보존) | 이사 전 매출은 서울, 이사 후 매출은 부산으로 정확히 집계됨 |

```sql
-- SCD Type 2용 Dimension: 같은 사용자가 기간별로 여러 행을 가짐
CREATE TABLE dim_user_scd2 (
    user_key    INT PRIMARY KEY,   -- 행마다 고유한 대리키 (surrogate key)
    user_id     INT  NOT NULL,     -- 운영 DB의 원래 사용자 ID
    region      TEXT NOT NULL,
    valid_from  DATE NOT NULL,
    valid_to    DATE,              -- NULL이면 현재 유효한 행
    is_current  BOOLEAN NOT NULL
);

INSERT INTO dim_user_scd2 VALUES
    (1001, 100, '서울', '2025-01-01', '2026-08-31', FALSE),
    (1002, 100, '부산', '2026-09-01', NULL,         TRUE);
```

Fact 테이블은 주문 시점에 유효했던 `user_key`(1001 또는 1002)를 가리키므로, 지역별 매출이 그 시점 기준으로 정확하게 나온다.

### 5.4 협업 상대

```
 원천 담당자 (DBA·백엔드 개발자)            데이터 소비자 (분석가·현업)
   "이 컬럼은 무슨 뜻?"                         "월별·카테고리별 매출이 필요해요"
   "status=3은 취소인가요?"                     "'활성 사용자' 정의는 이거예요"
            │                                            │
            └──────────▶  데이터 엔지니어  ◀──────────────┘
                      (DW 모델 설계·구현)
```

| 협업 상대              | 무엇을 도와주나                                           |
| ---------------------- | --------------------------------------------------------- |
| DBA·백엔드 개발자      | 원천 테이블의 의미, 스키마 변경 예정, 추출할 때 부하 조율 |
| 분석가·현업            | 필요한 지표, 비즈니스 용어 정의 (grain 결정의 근거)       |
| 데이터 거버넌스·보안팀 | 개인정보 컬럼 처리 방식                                   |

DBA의 도움은 **모델을 설계하는 데가 아니라 원천을 이해하는 데** 필요하다.

### 5.5 회사에 따라 다른 경우

1. **전통 대기업·금융권 (온프레미스 DW)**: Oracle·Teradata 기반 DW에서는 **데이터 아키텍트나 DW 모델러**라는 별도 직군이 논리 모델을 설계한다. 테이블스페이스·파티션·인덱스 같은 물리 설계는 **DBA가 맡는 경우**도 있다.
2. **클라우드 DW (Snowflake, BigQuery 등)**: 물리 설계 부담이 작아서(인덱스·스토리지 관리가 대부분 자동) 데이터 엔지니어가 논리부터 물리까지 다 한다.
3. **dbt를 쓰는 조직**: Analytics Engineer가 Fact/Dimension 모델링을 맡고, 데이터 엔지니어는 수집·인프라에 집중하는 식으로 다시 나누기도 한다.

> **논리 모델 vs 물리 모델**: 논리 모델은 "어떤 테이블에 어떤 컬럼이 있고 서로 어떻게 연결되나"이고, 물리 모델은 "그걸 디스크에 어떻게 배치하고 어떤 인덱스·파티션을 두나"다.

**판단 기준**: "누가 모델링하나"는 **저장소가 운영용인지 분석용인지**, 그리고 **물리 설계를 사람이 직접 관리해야 하는 환경인지**로 갈린다.
- 운영 DB는 DBA·백엔드 개발자가 모델링한다.
- 클라우드 DW는 데이터 엔지니어·Analytics Engineer가 직접 모델링한다.
- 온프레미스 대형 DW는 데이터 아키텍트가 논리 설계를, DBA가 물리 설계를 나눠 맡을 수 있다.

## 6. DW에 담는 데이터와 AI Agent의 KB

### 6.1 "DW는 수치를 다룬다"는 반만 맞다

DW는 수치 전용이 아니라 **정형 데이터(행·열로 정리된 데이터)를 분석하기 위한 저장소**이고, 텍스트 속성도 많이 담는다. 5.2절의 Star Schema를 다시 보면 이렇다.

| 테이블    | 담는 것                     | 예                                                     |
| --------- | --------------------------- | ------------------------------------------------------ |
| Fact      | **수치** (측정값)           | 금액 15,000 / 수량 2 / 할인액 1,000                    |
| Dimension | **텍스트 속성** (분석 기준) | 상품명 "무선 이어폰", 카테고리 "전자기기", 지역 "서울" |

정확히 말하면 DW의 대상은 **"수치를 텍스트 속성으로 잘라 집계하기 좋게 만든 정형 데이터"**다. DW에 맞지 않는 것은 텍스트가 아니라 **구조가 없는 긴 텍스트**다. 예를 들면 50쪽짜리 PDF 매뉴얼, Confluence 페이지, 상담 녹취록 같은 것들이다.

### 6.2 KB 데이터가 저장되는 곳

AI Agent의 KB용 원천인 문서·위키·매뉴얼 같은 비정형 텍스트는 보통 DW가 아니라 **Data Lake(원본 보관)와 Vector DB 또는 검색 엔진(검색용)**에 둔다.

```
 [원천]                [보관]               [가공]                     [검색용 저장]        [사용]
 PDF·매뉴얼 ──┐
 사내 위키 ───┼──▶ Data Lake (S3 등) ──▶ 파싱 → chunking ──▶ Vector DB / 검색 엔진 ──▶ AI Agent
 상담 로그 ───┘    원본 그대로 보관       → embedding 생성       (pgvector, OpenSearch,     (RAG)
                                                                  Pinecone, 관리형 KB)
```

| 구분        | DW                                      | Vector DB / 검색 엔진                              |
| ----------- | --------------------------------------- | -------------------------------------------------- |
| 질문 형태   | "3분기 서울 매출 합계는?" (정확한 집계) | "환불 규정이 어떻게 돼?" (의미가 비슷한 문서 찾기) |
| 검색 방식   | SQL 조건·집계                           | 벡터 유사도 + 키워드 검색                          |
| 데이터 단위 | 행 (주문 1건)                           | 문서 조각 (chunk)                                  |

**원본을 Data Lake에 따로 보관하는 이유**: chunking 방식이나 embedding 모델을 바꾸면 모든 문서를 처음부터 다시 처리해야 한다. Vector DB에는 가공된 조각만 있으므로 원본이 없으면 재처리할 수 없다.

관리형 RAG 검색 서비스(Bedrock KB, Vertex AI Search 등)의 비교는 [[managed-rag-search-services-comparison]]에 정리돼 있다.

### 6.3 DW와 AI Agent의 관계

DW가 Agent와 무관한 것은 아니다. 세 가지 연결점이 있다.

**① DW의 정형 데이터도 Agent의 지식 원천이 된다.** 다만 KB에 넣는 방식이 아니라 **Agent가 도구로 조회하는 방식**이다.

```
 사용자: "지난달 카테고리별 매출 알려줘"
    │
 AI Agent ──(SQL 생성 도구 호출, text-to-SQL)──▶ DW ──▶ 결과 표 ──▶ Agent가 요약해서 답변
```

수치 질문은 벡터 검색으로 문서를 찾는 것보다 DW에 SQL을 실행하는 편이 정확하다. 그래서 실무 Agent는 **"문서 질문은 RAG, 수치 질문은 DW 조회"**처럼 둘을 함께 쓰는 경우가 많다.

**② DW·Lakehouse 제품이 벡터 검색을 흡수하고 있다.** BigQuery는 `VECTOR_SEARCH` 함수를, Snowflake는 `VECTOR` 타입과 Cortex Search를, Databricks는 Vector Search를 제공하는 것으로 알려져 있다(확인 필요). 그래서 "DW에는 절대 안 둔다"기보다는 **"기본 자리는 Vector DB이고, 데이터 플랫폼을 하나로 합치려는 조직은 DW·Lakehouse 안에서 처리하기도 한다"**가 정확하다.

**③ KB 파이프라인도 데이터 엔지니어의 일이다.** 저장소가 DW가 아닐 뿐, 원천 수집, 파싱, chunking, embedding 생성, 문서가 바뀌면 다시 반영하는 증분 갱신까지 전부 파이프라인이다. 이 영역은 "AI 데이터 엔지니어링"이나 "unstructured data pipeline"이라는 이름으로 데이터 엔지니어 업무에 빠르게 들어오고 있다.

## 7. DW 데이터를 KB에 넣지 않는 진짜 이유

흔히 "embedding이 숫자에 약해서"라고 생각하기 쉽다. 그 이유도 있지만 주된 이유는 아니다. 더 근본적인 이유는 **RAG는 "비슷한 조각 몇 개를 찾아오는" 구조이고, DW에 던지는 질문은 "조건에 맞는 전부를 정확히 계산하는" 구조**라서 방식 자체가 맞지 않는다는 점이다. embedding이 숫자를 완벽하게 이해한다고 가정해도 이 문제는 그대로 남는다.

### 7.1 사고 실험: embedding이 완벽하다고 가정하면?

질문은 "3분기 서울 매출 합계는?"이고, 해당하는 주문은 **120만 건**이라고 하자.

```
 [RAG 방식]
 질문 ──embedding──▶ Vector DB ──top-k (예: 5개) 반환──▶ LLM
                     주문 120만 건을             "5건 합계 = 7만 원"
                     chunk로 저장                → ❌ 오답 (119만 9,995건 누락)

 [DW 방식]
 질문 ──text-to-SQL──▶ DW ──SUM으로 120만 건 전부 집계──▶ LLM
                       SELECT SUM(amount) ...        "합계 = 384억 원"
                                                     → ✅ 정답
```

두 방식의 차이는 쿼리 모양에 그대로 드러난다. pgvector(PostgreSQL의 벡터 검색 확장)로 쓰면 다음과 같다.

```sql
-- RAG: 질문 벡터와 가장 가까운 조각 5개만 가져옴 (설계상 "일부")
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE order_chunks (
    id        BIGSERIAL PRIMARY KEY,
    content   TEXT NOT NULL,          -- 예: "2026-08-20 서울 사용자가 러닝화 89,000원 구매"
    embedding vector(3) NOT NULL      -- 실제로는 768~3072차원. 예제라 3차원
);

INSERT INTO order_chunks (content, embedding) VALUES
    ('2026-07-15 서울 무선 이어폰 30,000원', '[0.9, 0.1, 0.2]'),
    ('2026-08-20 서울 러닝화 89,000원',     '[0.8, 0.2, 0.1]'),
    ('2026-08-20 부산 무선 이어폰 15,000원', '[0.3, 0.9, 0.2]');

SELECT content
FROM order_chunks
ORDER BY embedding <-> '[0.85, 0.15, 0.15]'   -- <-> : 벡터 간 거리
LIMIT 5;                                       -- top-k: 여기서 이미 "전부"가 아님
```

```sql
-- DW: 조건에 맞는 행을 전부 집계 (5.2절의 테이블 사용)
SELECT SUM(f.amount) AS revenue
FROM fact_order_items f
JOIN dim_date d ON f.date_key = d.date_key
JOIN dim_user u ON f.user_key = u.user_key
WHERE d.quarter = 3
  AND u.region  = '서울';
```

RAG 쪽의 `LIMIT 5`를 120만으로 늘리면 결과가 LLM context에 들어가지 않는다. 들어간다고 해도 LLM이 120만 개 숫자를 직접 더하면 틀릴 가능성이 크다. 즉 **검색 품질 문제가 아니라 "검색으로는 집계를 할 수 없다"는 구조 문제**다.

### 7.2 이유를 중요도 순으로

| 순위 | 이유                         | 설명                                                                                                                                        | embedding 품질과 관계      |
| ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 1    | **집계·완전성**              | SUM, COUNT, 평균, 순위는 해당 행을 전부 봐야 함. RAG는 일부만 가져옴                                                                        | 무관 (완벽해도 해결 안 됨) |
| 2    | **정확한 필터**              | "금액 ≥ 10,000", "2026-07-01 ~ 09-30" 같은 조건은 맞거나 틀리거나 둘 중 하나. 유사도 검색은 "비슷한 것"을 줌                                | 일부 관련                  |
| 3    | **숫자 표현력**              | embedding은 "15,000원"과 "15,001원", 심지어 "51,000원"도 비슷한 벡터로 만들기 쉬움. 크기·대소 관계를 잘 담지 못함 (모델마다 정도 차이 있음) | 직접 관련                  |
| 4    | **신선도·비용**              | DW는 매일 수백만 행이 바뀜. 매번 다시 embedding하면 비용이 크고 반영이 늦음                                                                 | 무관                       |
| 5    | **이미 더 좋은 도구가 있음** | 정형 데이터는 SQL이라는 정확한 질의 언어가 이미 있음. 굳이 근사 검색으로 바꿀 이유가 없음                                                   | 무관                       |

"embedding이 숫자에 약하다"는 3번에 해당한다. 맞는 지적이지만, 1·2번 때문에 그 전에 이미 RAG가 맞지 않는 방식이 된다.

**2번 실패 사례**: "10만 원 이상 주문"을 벡터 검색으로 찾으면 "89,000원" 주문이 상위에 섞여 나올 수 있다. 문장 구조가 비슷하기 때문이다. SQL의 `WHERE amount >= 100000`은 이런 실수를 하지 않는다.

### 7.3 예외: DW 데이터를 embedding하는 경우

DW 안에 있어도 **"의미로 찾을" 텍스트**라면 embedding 대상이 된다.

| DW 데이터                         | embedding 여부 | 이유                                         |
| --------------------------------- | -------------- | -------------------------------------------- |
| 주문 금액, 수량                   | ❌             | 집계 대상 → SQL로 조회                       |
| 상품 설명문, 리뷰 본문            | ✅             | "배터리 오래가는 이어폰 리뷰" 같은 의미 검색 |
| 고객 문의 내용                    | ✅             | "비슷한 불만 사례" 찾기                      |
| **테이블·컬럼 설명 (메타데이터)** | ✅             | text-to-SQL 정확도를 높이는 데 씀            |

마지막 행은 실무에서 자주 쓰는 패턴이다. 데이터 자체가 아니라 **"이 테이블에 무엇이 있는지"를 embedding**해 두고, Agent가 질문에 맞는 테이블을 먼저 찾은 뒤 SQL을 생성한다.

```
 질문: "지난달 환불률?" ──▶ 메타데이터 검색 (RAG) ──▶ "fact_refunds, fact_orders 테이블이 관련 있음"
                                                         │
                                         SQL 생성 ◀──────┘ ──▶ DW 조회 ──▶ 정확한 숫자
```

RAG와 DW는 경쟁 관계가 아니다. **RAG가 "어디를 볼지"를 찾고 DW가 "정확한 답"을 계산하는** 역할 분담이다.

### 7.4 판단 기준

데이터를 KB에 넣을지 고민될 때는 **"이 질문의 정답이 데이터 몇 개로 결정되나"**를 따져 본다.

| 질문 유형                         | 예                                        | 맞는 방식                                                 |
| --------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| 소수의 관련 조각으로 답이 나옴    | "규정이 뭐야", "비슷한 사례 있어?"        | Vector DB / 검색 엔진 + RAG                               |
| 조건에 맞는 전체를 봐야 답이 나옴 | "얼마", "몇 건", "상위 10개", "기간 비교" | DW + SQL 도구 (embedding 품질을 아무리 높여도 해결 안 됨) |

원본 문서는 어느 쪽이든 **Data Lake에 그대로 보관**해 둔다.

## 8. 데이터 엔지니어는 언제 필요한가

### 8.1 테이블 수가 기준이 아닌 이유

데이터 엔지니어가 필요한지는 **"데이터 원천이 몇 곳이고 얼마나 제각각인가"**와 **"데이터가 틀리거나 늦을 때 회사가 얼마나 손해를 보나"**로 정해진다. 테이블이 20개뿐인 회사라도 원천이 10곳이고 그 데이터로 매일 돈이 오가는 결정을 내린다면 필요하고, 테이블이 500개라도 서비스 DB 하나에서 가끔 리포트만 뽑는다면 아직 필요 없다.

| 구분                       | A사 (커머스 스타트업)                                                                                                | B사 (사내 업무 시스템)                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 운영 DB 테이블             | **25개**                                                                                                             | **400개**                                   |
| 데이터 원천                | 서비스 DB, 앱 이벤트 로그, 광고 3사 API, PG (Payment Gateway, 결제대행사) 정산 파일, CRM (고객관리 시스템) → **7곳** | 사내 ERP (전사 자원 관리 시스템) DB **1곳** |
| 데이터 소비                | 마케팅이 매일 광고 효율 보고 예산 조정, 추천 모델 운영                                                               | 월말에 리포트 몇 장                         |
| 틀리면?                    | 광고비 잘못 배분 → 매일 손실                                                                                         | 다시 뽑으면 됨                              |
| **데이터 엔지니어 필요성** | **높음**                                                                                                             | **낮음** (ERP 내장 리포트나 BI 도구로 충분) |

A사의 어려움은 테이블 수가 아니라 **서로 다른 7곳의 데이터를 이어 붙이는 일**이다. 광고 API의 "클릭"과 앱 로그의 "방문"과 DB의 "주문"을 같은 사용자로 연결하는 작업이 바로 데이터 엔지니어의 일이다.

### 8.2 판단 요소 6가지

| #   | 요소                   | 질문                                  | 데이터 엔지니어가 필요해지는 신호                          |
| --- | ---------------------- | ------------------------------------- | ---------------------------------------------------------- |
| 1   | **원천의 수·이질성**   | 데이터가 몇 곳에서, 어떤 형태로 오나? | DB + 로그 + 외부 API + 파일처럼 3곳 이상이 섞임            |
| 2   | **소비자와 의존도**    | 누가, 얼마나 자주, 어떤 결정에 쓰나?  | 여러 팀이 매일 데이터로 의사결정함                         |
| 3   | **정확성·신선도 요구** | 틀리거나 늦으면 무슨 일이 나나?       | 매출·정산·규제 보고에 쓰임, 실시간성이 필요함              |
| 4   | **데이터 제품 여부**   | 데이터가 서비스 기능 자체인가?        | 추천·검색·AI Agent·이상거래 탐지가 있음                    |
| 5   | **볼륨·속도**          | 단일 DB와 단순 쿼리로 감당되나?       | 분석 쿼리가 운영 DB를 느리게 만듦, 이벤트가 하루 수천만 건 |
| 6   | **현재 숨은 비용**     | 지금 누가 그 일을 대신하고 있나?      | 백엔드 개발자나 분석가가 데이터 정리에 시간을 많이 씀      |

5번 볼륨이 흔히 떠오르는 기준이지만, 실제로는 **1·2·3번이 먼저** 신호를 보내는 경우가 많다. 클라우드 DW가 볼륨 문제를 상당 부분 흡수하기 때문이다.

**가장 흔한 경로와 두 번째 경로**

```
 [경로 1: 의사결정 수요]
 지속적인 데이터 기반 의사결정 ─── 왜 필요한가 (수요)        ← 요소 2
 여러 원천에서 제각각 수집 ────── 무엇이 어려운가 (원인)     ← 요소 1
 숫자가 달라짐·늦음·빠짐 ──────── 어떤 증상이 보이나          ← 요소 3
 백엔드 엔지니어·분석가 업무 과중 ── 지금 누가 비용을 치르나   ← 요소 6

 [경로 2: 데이터 제품]
 추천·검색·AI Agent KB 운영 ───── 파이프라인이 곧 제품의 일부  ← 요소 4
```

경로 2는 사람이 내리는 비즈니스 결정과 무관하게 데이터 엔지니어가 필요한 경우다. 예를 들어 사내 문서로 AI Agent를 운영하는 회사는 대시보드가 하나도 없어도 문서 수집, chunking, embedding, 증분 갱신 파이프라인을 누군가 만들고 지켜야 한다.

### 8.3 현장에서 보이는 신호

이런 말이 들리기 시작하면 필요한 시점이다.

| 들리는 말                                                 | 의미                             | 관련 요소 |
| --------------------------------------------------------- | -------------------------------- | --------- |
| "회의 때마다 팀마다 숫자가 달라요"                        | 지표 정의와 원천이 통일되지 않음 | 1, 3      |
| "어제 실적이 오후 3시에나 나와요"                         | 데이터가 늦음                    | 3         |
| "광고 데이터가 일주일 빠졌는데 아무도 몰랐어요"           | 모니터링과 품질 관리가 없음      | 3         |
| "분석 쿼리 돌렸더니 서비스가 느려졌어요"                  | 운영 DB와 분석을 분리해야 함     | 5         |
| "백엔드 개발자가 리포트용 쿼리 짜느라 기능 개발이 밀려요" | 숨은 비용이 생김                 | 6         |
| "분석가가 시간의 대부분을 엑셀로 데이터 합치는 데 써요"   | 파이프라인이 없음                | 1, 6      |

과중해지는 쪽은 백엔드 엔지니어일 수도, 분석가일 수도 있다. 어느 쪽이든 **본업 대신 데이터 정리를 하고 있다**는 것이 핵심 신호다.

### 8.4 회사 단계별 선택과 채용 전 대안

```
 [초기]                    [성장]                         [확장]
 원천 1~2곳               원천 3곳 이상, 팀별 데이터 소비    데이터 제품·AI 운영
    │                          │                              │
    ▼                          ▼                              ▼
 데이터 엔지니어 채용 불필요  데이터 엔지니어 1명               데이터 엔지니어 팀
 - 운영 DB 읽기 전용 복제본   (또는 Analytics Engineer)        (플랫폼 / 도메인 분리)
   + BI 도구                - 관리형 수집 도구 + 클라우드 DW   - 스트리밍, 데이터 품질 체계
 - 백엔드 개발자가 겸임      - dbt로 지표 정의 통일             - KB 파이프라인 등
```

**채용 전에 시도할 수 있는 대안**

| 대안                                    | 해결하는 것                                       |
| --------------------------------------- | ------------------------------------------------- |
| 관리형 수집 도구 (Fivetran, Airbyte 등) | 외부 API나 DB를 DW로 복사하는 일을 코드 없이 처리 |
| 클라우드 DW + dbt                       | 분석가가 SQL만으로 변환 작업을 맡을 수 있음       |
| 외부 컨설팅으로 초기 구축               | 처음 기반만 잡고 운영은 내부에서 함               |

이 도구들로 버티다가 **"도구를 엮고 관리하는 일 자체가 누군가의 본업이 될 만큼 커졌을 때"**가 첫 데이터 엔지니어를 뽑을 시점이다.

이 판단 요소들은 업계에서 흔히 쓰는 기준이며, "원천 몇 곳 이상이면 채용" 같은 객관적인 임계값이 정해져 있는 것은 아니다.

### 8.5 한 문장 요약

> **데이터가 의사결정이나 제품에 계속 쓰이는데, 그 데이터를 모으고 맞추고 지키는 일이 다른 사람의 부업으로는 더 이상 감당되지 않을 때** 데이터 엔지니어가 필요하다.

| DW 모델링 주체                  | 클라우드 DW는 데이터 엔지니어·Analytics Engineer가 직접. DBA는 원천 이해에 협력                   | 5        |

| DW 데이터를 KB에 넣지 않는 이유 | 주 이유는 "검색(top-k)으로는 집계(전체)를 할 수 없다"는 구조 문제. embedding의 숫자 약점은 부차적 | 7        |
| 채용 판단                       | 테이블 수가 아니라 원천의 이질성, 데이터 의존도, 오류 비용, 데이터 제품 여부, 숨은 비용           | 8        |
