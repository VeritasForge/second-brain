## 1. 이 문서가 다루는 것

개발 서버(`dev-server`)는 랜선(유선)으로 사내 네트워크에 연결되어 있다. 이 서버의 유선 연결을 사내 Wi-Fi(`corp_work`)로 **대체**하려고 시도했고, 그 과정에서 다음과 같은 결과를 얻었다.

| 단계         | 결과                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| Wi-Fi 인증   | ✅ 성공했다. 계정 ID와 비밀번호를 사용하는 회사 인증 방식(802.1X)을 통과했다                                                          |
| IP 주소 배정 | ✅ 성공했다. `10.0.30.25`를 자동으로 배정받았다                                                                                       |
| 실제 통신    | ❌ 연결 직후에는 통신이 되었지만, 수십 분 안에 사내 접근 제어 시스템이 서버의 무선 장치를 제한 대상으로 처리해서 통신이 차단되었다    |
| 결론         | 서버나 PC의 설정으로는 해결할 수 없고, 보안팀(네트워크 관리자)이 서버의 무선 장치를 승인해 주어야 한다. 그때까지 유선은 유지해야 한다 |

이 문서는 이 사례를 따라가면서, 결과를 이해하는 데 필요한 네트워크 기초(3장), 회사 Wi-Fi의 인증 구조(4장), 접근 제어 시스템(5장)을 먼저 설명하고, 실제 작업과 진단 과정(6~7장), 앞으로 해야 할 일(8~9장)을 정리한다.

## 2. 대상 환경

### 서버

| 항목               | 값                                                                           |
| ------------------ | ---------------------------------------------------------------------------- |
| 접속 이름          | `dev-server` (PC의 `~/.ssh/config`에 등록된 이름)                            |
| 호스트명           | `dev-host`                                                                   |
| 운영체제           | Ubuntu 24.04 LTS                                                             |
| 유선 장치          | `eno1.10`, 고정 주소 `10.0.10.51/24`                                         |
| 무선 장치          | `wlp3s0`, MAC 주소 `aa:bb:cc:dd:ee:ff`                                       |

네트워크 관리에 관여하는 세 프로그램의 역할은 다음과 같다.

| 프로그램         | 역할                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| netplan          | 사람이 `/etc/netplan/*.yaml`에 적은 설정을 읽어서, 아래 두 프로그램이 이해하는 설정 파일로 변환한다 |
| systemd-networkd | 장치에 IP 주소와 경로를 실제로 적용하고, DHCP로 주소를 받아 온다                                    |
| wpa_supplicant   | Wi-Fi 공유기와의 연결과 인증을 담당한다                                                             |

### 네트워크 대역

이 사례에는 세 개의 네트워크 대역이 등장한다. "대역"은 같은 네트워크에 속하는 IP 주소의 범위를 뜻하며, 주소 뒤의 `/24`나 `/23`이 그 범위의 크기를 나타낸다(`/24`는 주소 256개, `/23`은 512개).

| 대역           | 용도                 | gateway     | 여기에 속한 기기                                                             |
| -------------- | -------------------- | ----------- | ---------------------------------------------------------------------------- |
| `10.0.10.0/24` | 서버의 유선 네트워크 | `10.0.10.1` | 서버의 유선 장치 (`10.0.10.51`)                                              |
| `10.0.20.0/24` | Wi-Fi `corp_admin`   | `10.0.20.1` | 작업용 Mac (`10.0.20.18`)                                                    |
| `10.0.30.0/23` | Wi-Fi `corp_work`    | `10.0.30.1` | 서버의 무선 장치 (`10.0.30.25`), Mac을 이 Wi-Fi로 바꾸었을 때 (`10.0.30.19`) |

gateway는 다른 대역으로 나가는 관문 역할을 하는 장비이다. 3.2절에서 자세히 설명한다.

## 3. 네트워크 기초

### 3.1 IP 주소와 MAC 주소: 둘 다 필요한 이유

기기들은 서로를 두 가지 주소로 구분한다.

| 주소     | 나타내는 것                                 | 비유                                                          | 예시                |
| -------- | ------------------------------------------- | ------------------------------------------------------------- | ------------------- |
| IP 주소  | 데이터가 **최종적으로 누구에게 가는가**     | 받는 사람의 이름, 택배 송장의 최종 배송지                     | `10.0.10.51`        |
| MAC 주소 | **지금 이 구간에서 누구에게 건네야 하는가** | 그 사람이 앉아 있는 자리 번호, 물건을 넘겨받는 다음 물류 거점 | `aa:bb:cc:dd:ee:ff` |

IP 주소만으로 충분하지 않은 이유는, 데이터가 여러 장치를 차례로 거쳐서 전달되기 때문이다. 작업용 Mac에서 서버로 접속하는 경우를 보면, 데이터의 최종 목적지는 서버인데 실제로 건네받아야 하는 장치는 gateway이다.

- 받는 주소를 서버의 IP로만 적으면, 같은 네트워크에 서버가 없으므로 아무도 받지 않는다.
- 받는 주소를 gateway의 IP로 적으면, gateway는 데이터를 받기는 하지만 그것을 어디로 전달해야 하는지 알 수 없다.

그래서 주소를 두 겹으로 적는다. 최종 배송지(IP)는 끝까지 바뀌지 않고, 구간마다 넘겨받는 상대(MAC)만 바뀐다.

```
                구간 1                          구간 2
        Mac ──────────→ gateway ──────────→ 서버

IP  (최종 목적지)  받는 이: 10.0.10.51          받는 이: 10.0.10.51        ← 끝까지 그대로
MAC (이번 구간)    받는 이: gateway 의 MAC      받는 이: 서버의 MAC         ← 구간마다 바뀜
```

MAC 주소가 필요한 이유는 이 밖에도 세 가지가 있다.

| 이유                                        | 설명                                                                                                                                                                   | 이 사례에서 본 장면                                                                                                                                                                                         |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 수신 여부를 빠르게 가려내기 위해            | Wi-Fi는 전파를 공유하므로 주변의 모든 기기가 같은 신호를 수신한다. 각 기기의 네트워크 장치는 신호에 적힌 MAC 주소가 자신의 것인지를 보고 받을지 버릴지를 즉시 결정한다 | 서버의 무선 장치는 다른 기기들의 통신을 수신하지만 자신에게 온 것만 처리한다                                                                                                                                |
| IP 주소를 받기 전에도 통신해야 하기 때문에  | 기기는 네트워크에 처음 연결될 때 IP 주소가 없다. IP 주소를 배정받는 과정(3.3절의 DHCP) 자체가 MAC 주소를 사용해서 이루어진다                                           | 서버의 무선 장치는 Wi-Fi 인증에 성공한 뒤에야 `10.0.30.25`를 받았다                                                                                                                                         |
| IP 주소는 바뀌지만 장치는 그대로이기 때문에 | IP 주소는 연결하는 네트워크에 따라 달라진다. MAC 주소는 장치에 붙어 있는 번호라서 "어느 장치인가"를 식별하는 기준이 된다                                               | Mac의 IP는 Wi-Fi를 바꿀 때마다 `10.0.20.18`과 `10.0.30.19` 사이에서 달라졌다. 관리자가 특정 장치에 항상 같은 IP를 배정하도록 예약하거나, 접근 제어 시스템에 기기를 등록할 때에도 MAC 주소를 기준으로 삼는다 |

### 3.2 ARP: IP 주소로 MAC 주소를 찾는 방법

데이터를 건네려면 상대의 MAC 주소가 필요한데, 보내는 쪽은 IP 주소만 알고 있다. ARP(Address Resolution Protocol)는 IP 주소로 MAC 주소를 알아내는 규약이다. 같은 네트워크에 있는 **모든 기기에게** 질문을 보내고, 해당하는 기기가 응답한다.

```
보내는 기기 ──(모두에게)──→  "10.0.20.1 을 쓰는 분, MAC 주소가 어떻게 됩니까?"
해당 기기   ──(질문자에게)─→  "저입니다. 제 MAC 주소는 … 입니다."
```

질문을 특정 상대에게 보내지 못하고 모두에게 보내는 이유는, MAC 주소를 모르는 상태에서는 그 상대에게만 전달할 방법이 없기 때문이다.

**ARP는 같은 네트워크 안에서만 통한다.** 모두에게 보내는 질문은 다른 대역으로 넘어가지 않는다. 그래서 상대가 다른 대역에 있으면, 보내는 기기는 상대가 아니라 gateway의 MAC 주소를 찾아서 데이터를 gateway에게 맡긴다. 상대의 MAC 주소를 찾는 일은 상대와 같은 대역에 있는 gateway가 대신한다.

```
   10.0.20.x 네트워크                       10.0.10.x 네트워크
┌──────────────────────────┐          ┌──────────────────────────┐
│  Mac ──ARP①──→ gateway   │          │  gateway ──ARP②──→ 서버   │
│ .20.18          .20.1    │ ═══════→ │   .10.1           .10.51 │
└──────────────────────────┘  전달     └──────────────────────────┘

ARP①: Mac 이 묻는다.     "10.0.20.1(gateway) 의 MAC 주소는?"
ARP②: gateway 가 묻는다. "10.0.10.51(서버) 의 MAC 주소는?"
```

실제로 Mac의 ARP 기록을 조회하면 이 구조가 그대로 나타난다.

| 조회한 것            | 결과                                   | 의미                                                             |
| -------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| gateway(`10.0.20.1`) | 기록 있음                              | Mac이 ARP로 찾은 상대는 gateway이다                              |
| 서버(`10.0.10.51`)   | 기록 없음                              | SSH 접속이 정상적으로 되는 중에도 Mac은 서버의 MAC 주소를 모른다 |
| 서버까지의 경로 추적 | 1번째 `10.0.20.1` → 2번째 `10.0.10.51` | 데이터가 gateway를 거쳐서 전달된다                               |

반대로 Mac을 `corp_work`로 바꾸었을 때에는 Mac(`10.0.30.19`)과 서버의 무선 IP(`10.0.30.25`)가 같은 대역에 있었으므로, Mac이 gateway를 거치지 않고 직접 "10.0.30.25의 주인이 누구인가"를 물었고 Mac의 ARP 기록에 그 주소가 남았다.

**ARP에는 검증 절차가 없다.** 응답한 기기가 정말 그 IP의 주인인지를 확인하지 않고, 응답을 그대로 믿는다. 이 특성은 5.3절에서 설명하는 접근 제어 방식의 바탕이 된다.

### 3.3 DHCP: 통신 설정을 자동으로 받는 방법

DHCP(Dynamic Host Configuration Protocol)는 네트워크에 연결된 기기에게 통신에 필요한 설정을 자동으로 나누어 주는 규약이다. 기기가 통신하려면 다음 네 가지 정보가 필요하다. DHCP가 없다면 기기를 연결할 때마다 사람이 직접 입력해야 하고, 두 기기에 같은 주소를 입력하는 실수가 생기면 양쪽의 통신이 모두 끊긴다.

| 필요한 정보   | 의미                           | 서버의 무선 장치가 받은 값                  |
| ------------- | ------------------------------ | ------------------------------------------- |
| IP 주소       | 이 기기의 주소                 | `10.0.30.25`                                |
| 서브넷 마스크 | 같은 네트워크의 범위           | `255.255.254.0` (`10.0.30.0`~`10.0.31.255`) |
| gateway       | 다른 대역으로 나가는 관문      | `10.0.30.1`                                 |
| DNS 서버      | 이름을 주소로 바꾸어 주는 서버 | 통신사의 공개 DNS 주소, `8.8.8.8`           |

주소를 받는 과정은 네 번의 대화로 이루어진다.

```
 새로 연결된 기기                                DHCP 서버 (10.0.30.1)
 (아직 IP 가 없음)
      │ ① "주소를 나누어 주는 분 계십니까?" (모두에게)      │
      │──────────────────────────────────────────────→│
      │ ② "10.0.30.25 를 쓰시겠습니까?"                  │  빈 주소 중 하나를 고름
      │←──────────────────────────────────────────────│
      │ ③ "네, 그 주소를 쓰겠습니다"                      │
      │──────────────────────────────────────────────→│
      │ ④ "확정합니다. 1주일 동안 사용하십시오"            │  장부에 기록: 이 MAC → 이 주소
      │←──────────────────────────────────────────────│
```

④에서 정해지는 사용 기간을 임대 기간이라고 한다. 서버가 받은 주소의 임대 기간은 1주일이며, 절반(3일 12시간)이 지나면 서버가 자동으로 연장을 요청한다. 기기가 오랫동안 꺼져 있어서 연장하지 못하면 그 주소는 회수되어 다른 기기에게 배정될 수 있다. 자동으로 받은 주소가 나중에 바뀔 수 있는 이유가 이것이다.

이 서버의 유선과 무선은 주소를 정하는 방식이 서로 다르다.

| 구분               | 유선 `eno1.10`                      | 무선 `wlp3s0`    |
| ------------------ | ----------------------------------- | ---------------- |
| 주소를 정한 방식   | 사람이 설정 파일에 직접 입력 (고정) | DHCP로 자동 배정 |
| 경로 조회 시 표시  | `proto static`                      | `proto dhcp`     |
| 주소가 바뀔 가능성 | 없음                                | 있음             |

**서버 쪽의 DHCP 설정**은 "자동으로 받겠다"라고 선언하는 한 줄이다.

```yaml
network:
  version: 2
  wifis:
    wlp3s0:
      dhcp4: true      # IPv4 주소를 DHCP 로 받겠다는 뜻
```

**IP를 고정하는 방법**은 두 가지이다.

| 방법                | 설정하는 곳                 | 동작                                                                                                                                 | 주의할 점                                                                                                                                                      |
| ------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DHCP 예약 (권장)    | DHCP 서버 (네트워크 관리자) | DHCP 서버의 장부에 "MAC `aa:bb:cc:dd:ee:ff` → 항상 이 주소"라는 규칙을 등록한다. 서버는 그대로 자동으로 받지만 매번 같은 주소가 온다 | 서버의 설정을 바꿀 필요가 없다                                                                                                                                 |
| 고정 주소 직접 입력 | 서버의 설정 파일            | `dhcp4: true` 대신 주소, gateway, DNS를 직접 적는다                                                                                  | DHCP 서버는 이 사실을 모르기 때문에 같은 주소를 다른 기기에게 배정할 수 있고, 그러면 주소가 충돌한다. 관리자가 그 주소를 자동 배정 범위에서 제외해 주어야 한다 |

고정 주소를 직접 입력하는 설정은 다음과 같은 형태이다(값은 형태를 보이기 위한 예시이다).

```yaml
network:
  version: 2
  wifis:
    wlp3s0:
      dhcp4: false
      addresses: [10.0.30.50/23]           # 예시 값
      routes:
        - to: default
          via: 10.0.30.1
      nameservers:
        addresses: [8.8.8.8, 1.1.1.1]
```

두 방법 모두 관리자의 조치가 필요하므로, 서버의 설정을 바꾸지 않아도 되는 DHCP 예약이 더 간단하다. 이 네트워크에서는 gateway(`10.0.30.1`)가 DHCP 서버의 역할도 함께 하고 있다.

### 3.4 ping과 기준 상대 `1.1.1.1`

ping은 상대에게 "들리면 대답해 달라"라는 짧은 신호를 보내고, 대답이 돌아오는지와 걸린 시간을 측정하는 도구이다. 여러 번 보내면 몇 번이 유실되었는지도 알 수 있다.

```
서버 ──"들립니까?"──→ 1.1.1.1
서버 ←──"들립니다"─── 1.1.1.1      → 응답 시간 6ms, 유실 0%
```

`1.1.1.1`은 Cloudflare가 전 세계에 공개해서 운영하는 서버의 주소로, 항상 켜져 있고 ping에 응답한다. 그래서 "이 기기가 인터넷까지 통신할 수 있는가"를 확인하는 **기준 상대**로 쓴다. 응답 여부가 불확실한 상대를 기준으로 삼으면, 응답이 없을 때 이쪽의 문제인지 상대의 문제인지 구분할 수 없다. 같은 용도로 Google의 `8.8.8.8`도 많이 쓴다.

**이름이 아닌 숫자 주소를 쓰는 이유**는 원인을 분리하기 위해서이다. `ping example.com`이 실패하면 원인이 다음 둘 중 무엇인지 알 수 없다.

| 단계                  | 하는 일                                  | 실패할 수 있는 원인 |
| --------------------- | ---------------------------------------- | ------------------- |
| ① 이름 → 주소 변환    | DNS 서버에 `example.com`의 주소를 묻는다 | DNS 문제            |
| ② 그 주소로 신호 전송 | 실제 통신 경로를 사용한다                | 경로 문제           |

숫자 주소로 직접 보내면 ①을 건너뛰므로, 실패했을 때 원인이 경로에 있다고 바로 판단할 수 있다. DNS는 이름 조회 명령으로 따로 확인한다.

**목적지를 바꾸어 가며 문제 구간을 좁힌다.**

```
서버 ─────────→ gateway ─────────→ 인터넷의 서버
             (10.0.30.1)            (1.1.1.1)

gateway 로 ping  : 서버와 같은 네트워크 안의 구간이 정상인가
1.1.1.1 로 ping  : gateway 너머 인터넷까지 정상인가
```

**같은 목적지로 경로만 바꾸어 비교한다.** `ping -I <장치>` 옵션으로 사용할 장치를 지정하면, 목적지가 같고 경로만 다른 두 시험을 나란히 할 수 있다. 결과에 차이가 나면 그 원인은 경로에 있다.

```bash
ping -I wlp3s0  -c 25 1.1.1.1   # 무선으로
ping -I eno1.10 -c 25 1.1.1.1   # 유선으로
```

**ping의 한계**: ping이 성공한다고 실제 서비스가 동작한다는 보장은 없고, 반대도 마찬가지이다. ping이 사용하는 신호의 종류(ICMP)는 웹이나 SSH가 사용하는 종류(TCP)와 달라서, 네트워크 장비가 한쪽만 허용하거나 차단할 수 있다. 이 사례에서도 무선 경로에서 ping은 100% 유실되었지만 DNS 조회는 정상이었다. ping은 첫 단계의 확인으로 쓰고, 실제로 사용하려는 통신(SSH, 웹 요청)은 따로 시험해야 한다.

## 4. 회사 Wi-Fi의 인증 방식 (802.1X)

### 4.1 집의 방식과 회사의 방식

| 구분                      | 집 (WPA2 Personal, 개인용)                  | 회사 (WPA2 Enterprise, 기업용)     |
| ------------------------- | ------------------------------------------- | ---------------------------------- |
| 비밀번호                  | 모든 사람이 하나를 공유한다                 | 사람마다 ID와 비밀번호가 다르다    |
| 비밀번호를 확인하는 곳    | 공유기                                      | 인증 서버 (공유기는 전달만 한다)   |
| 누가 접속했는지           | 알 수 없다                                  | 계정별로 기록이 남는다             |
| 한 사람의 접속을 막으려면 | 비밀번호를 바꾸고 모두에게 다시 알려야 한다 | 그 사람의 계정만 비활성화하면 된다 |

집의 방식을 회사에서 쓰면 직원 한 명이 퇴사할 때마다 전 직원의 Wi-Fi 비밀번호를 바꾸어야 하고, 사고가 났을 때 누구의 기기였는지 추적할 수 없다. 이 문제를 해결하려고 "확인하는 일"을 공유기에서 떼어 내어 중앙의 인증 서버로 옮긴 것이 회사의 방식이다. 이 방식의 표준 이름이 802.1X이다.

### 4.2 세 장치의 역할과 인증 순서

인증에는 세 장치가 참여한다. 인증 서버는 RADIUS(Remote Authentication Dial-In User Service)라는 규약으로 공유기와 통신하므로 흔히 "RADIUS 서버"라고 부른다.

```
 접속하려는 기기            공유기(AP)                  인증 서버(RADIUS)
 (서버의 무선 장치)        (전달만 하는 문지기)         (계정 명부를 가진 곳)
       │                       │                            │
       │ ① 접속 요청            │                            │
       │──────────────────────→│                            │
       │ ② "먼저 인증하십시오"   │                            │
       │←──────────────────────│                            │
       │                       │                            │
       │ ③ 인증 서버가 자신의 인증서를 제시하고, 둘 사이에 암호화 통로를 만듦
       │←═══════════════ (공유기는 내용을 볼 수 없음) ═══════════│
       │                       │                            │
       │ ④ 암호화 통로 안에서 ID 와 비밀번호를 확인               │
       │═══════════════════════════════════════════════════→│ 명부와 대조
       │                       │                            │
       │                       │ ⑤ "통과시켜도 됩니다"         │
       │                       │←───────────────────────────│
       │ ⑥ 이 기기만 사용하는 암호화 키를 만들고 통신 시작         │
       │←─────────────────────→│                            │
```

④에서 비밀번호 자체를 보내지는 않는다. 인증 서버가 임의의 값을 보내면, 기기는 그 값과 비밀번호를 조합해서 계산한 결과를 돌려보낸다. 비밀번호를 아는 쪽만 올바른 결과를 계산할 수 있으므로, 인증 서버는 비밀번호를 받지 않고도 상대가 비밀번호를 알고 있는지를 확인할 수 있다.

이 과정에 등장하는 규약의 이름은 다음과 같다.

| 이름                                     | 의미                                                                                |
| ---------------------------------------- | ----------------------------------------------------------------------------------- |
| EAP (Extensible Authentication Protocol) | 인증 대화 전체의 규약. 여러 가지 세부 방식을 담을 수 있다                           |
| PEAP (Protected EAP)                     | 암호화 통로를 먼저 만들고(③) 그 안에서 인증하는(④) 방식. 이 사례의 Wi-Fi가 사용한다 |
| MSCHAPv2                                 | ④에서 비밀번호를 보내지 않고 확인하는 방식의 이름                                   |

### 4.3 인증 서버는 어디에서 오는가

인증 서버는 회사가 직접 개발하지도 않고 공유기에 딸려 오지도 않으며, 이미 만들어져 있는 별도의 제품이나 소프트웨어를 설치해서 쓰는 것이 일반적이다.

| 방법                                 | 설명                                                                           | 대표적인 예                                 |
| ------------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------- |
| 무료 공개 소프트웨어를 서버에 설치   | 비용은 들지 않지만 직접 설정하고 관리해야 한다                                 | FreeRADIUS                                  |
| 서버용 운영체제에 포함된 기능을 사용 | Windows 기반의 계정 시스템을 쓰는 회사에서 그 운영체제의 인증 서버 기능을 켠다 | Windows Server의 NPS(Network Policy Server) |
| 보안 제품에 포함된 것을 사용         | 접근 제어 제품이 인증 서버 기능을 함께 제공한다                                | Cisco ISE, Aruba ClearPass 등               |
| 네트워크 장비에 내장된 것을 사용     | 일부 기업용 장비에 간단한 인증 서버가 들어 있다. 소규모 사무실에서 쓴다        | 제조사마다 다름                             |

가정용 공유기의 설정 화면에 "WPA2 Enterprise" 항목이 있더라도 인증 서버가 내장되어 있다는 뜻은 아니다. 인증 서버의 주소를 입력하는 칸이 있을 뿐이다.

서로 다른 회사의 제품끼리 연결되는 이유는 RADIUS가 공개된 표준이기 때문이다. 관리자는 공유기에 두 가지만 설정한다.

```
 공유기(AP) 의 설정                         인증 서버
┌─────────────────────────────┐         ┌──────────────────────┐
│ 인증 서버의 주소 : 10.x.x.x   │ ──────→ │ 계정 명부              │
│ 서로를 확인할 비밀 값 : ****   │ RADIUS  │ (직원별 ID·비밀번호)    │
└─────────────────────────────┘ ←────── └──────────────────────┘
```

공유기가 여러 대이더라도 모두 같은 인증 서버를 가리키도록 설정하면, 직원은 어느 공유기에 연결되든 같은 계정으로 인증을 받는다.

**계정 명부**를 두는 방식은 회사마다 다르다. 인증 서버 안에 Wi-Fi 전용 계정을 따로 만드는 방식이 있고, 회사의 통합 계정 시스템을 인증 서버가 조회하도록 연결하는 방식이 있다. 뒤의 방식에서는 직원이 하나의 계정으로 Wi-Fi와 다른 시스템을 함께 사용하고, 퇴사 처리로 계정이 비활성화되면 Wi-Fi 접속도 함께 차단된다.

**이 사례의 경우**: 인증 서버가 제시한 인증서의 이름이 사내 접근 제어 제품의 이름이었으므로, 위 표의 세 번째 방법처럼 인증 서버 역할을 그 제품이 하고 있다고 볼 수 있다. 계정 명부가 그 제품 안에 따로 있는지 다른 사내 계정 시스템과 연결되어 있는지는 확인되지 않았다.

### 4.4 인증서: 무엇이고 어떻게 검증하는가

4.2절의 ③ 단계에서 인증 서버가 인증서를 제시하는 것은 정상적인 절차이다. 집의 방식에는 이 단계가 없다.

#### 인증서가 해결하는 두 가지 문제

| 문제        | 설명                                                                                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 가짜 공유기 | Wi-Fi 이름은 누구나 마음대로 정할 수 있어서, 공격자가 같은 이름의 가짜 공유기를 만들 수 있다. 기기가 상대를 확인하지 않고 인증을 진행하면 그 내용이 공격자에게 넘어간다 |
| 엿보기      | Wi-Fi는 전파이므로 주변의 누구나 신호를 수신할 수 있다. 암호화 통로가 없으면 인증 과정의 내용이 노출된다                                                                |

#### 인증서의 구성

인증서는 **공개 열쇠 + 그 열쇠의 주인이 누구인지 + 발급 기관의 서명**을 하나로 묶은 문서이다. 핵심 내용물은 공개 열쇠이지만, 인증서의 가치는 "이 공개 열쇠가 누구의 것인지를 보증한다"라는 데에 있다.

```
공개 열쇠만 받은 경우              인증서를 받은 경우
┌──────────────────┐            ┌─────────────────────────────────┐
│ 3A 9F 1C ... (숫자) │            │ 이름      : 인증 서버의 이름        │ ← 누구의 것인가
└──────────────────┘            │ 공개 열쇠  : 3A 9F 1C ...         │ ← 내용물
 → 누구의 열쇠인지 알 수 없음        │ 유효 기간  : ~ 까지               │
                                │ 발급 기관  : 발급 기관(CA)의 이름   │
                                │ 서명      : (CA 가 위 내용 전체에 찍음) │ ← 보증
                                └─────────────────────────────────┘
```

| 신분증           | 인증서                | 역할                                                                                                                     |
| ---------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 이름             | 서버의 이름           | 누구의 인증서인지 나타낸다                                                                                               |
| 사진             | 공개 열쇠             | 그 서버만 가진 비밀 열쇠와 짝을 이루는 값. 상대가 비밀 열쇠를 실제로 가지고 있는지 확인하고 암호화 통로를 만드는 데 쓴다 |
| 발급 기관의 직인 | 발급 기관의 전자 서명 | 내용이 위조되지 않았음을 보증한다                                                                                        |

공개 열쇠만 있으면 공격자가 자신의 공개 열쇠를 내밀면서 "제가 회사의 인증 서버입니다"라고 주장해도 구분할 수 없다. 서명이 이름과 공개 열쇠를 함께 덮고 있기 때문에, 이름은 그대로 두고 공개 열쇠만 바꾸면 서명이 맞지 않게 된다.

인증서를 발급하는 기관을 CA(Certificate Authority)라고 한다. 웹 브라우저의 주소 표시줄에 자물쇠가 표시되는 HTTPS도 같은 원리로 동작한다.

#### 검증하는 방식: "같은지 비교"가 아니라 "서명 확인"

기기에 미리 저장해 두는 것은 인증 서버의 인증서가 아니라 **CA의 인증서**이다. 상대의 신분증 사본을 보관하는 것이 아니라, 발급 기관의 직인 견본을 보관하는 것에 해당한다.

| 인증서             | 누구의 것인가 | 기기가 하는 일                                       |
| ------------------ | ------------- | ---------------------------------------------------- |
| CA의 인증서        | 발급 기관(CA) | 미리 받아서 저장해 둔다                              |
| 인증 서버의 인증서 | 인증 서버     | 접속할 때마다 인증 서버가 보내 준다. 저장하지 않는다 |

```
[미리 준비]  기기에 저장: CA 의 인증서 (안에 "CA 의 공개 열쇠"가 들어 있음)

[접속할 때]  인증 서버 ──→ "제 인증서입니다"

 기기의 검증
  ① 서명 확인   : 저장해 둔 CA 의 공개 열쇠로 서명을 풀어서, 인증서의 내용과 맞는지 계산
                  → 맞으면 "이 CA 가 발급했고, 내용이 위조되지 않았다"
  ② 기간 확인   : 유효 기간이 지나지 않았는가
  ③ 소유 확인   : 상대가 이 인증서와 짝을 이루는 비밀 열쇠를 실제로 가지고 있는가
                  → 인증서는 공개 정보라서 누구나 복사할 수 있으므로 이 확인이 필요하다
  하나라도 실패하면 → 연결을 중단하고, ID·비밀번호 확인 단계로 넘어가지 않음
```

서명은 CA의 비밀 열쇠로만 만들 수 있고, CA의 공개 열쇠로는 그 서명이 맞는지 확인만 할 수 있다. 공격자가 가짜 인증 서버를 세우더라도 CA의 비밀 열쇠가 없으므로 올바른 서명이 찍힌 인증서를 만들 수 없다.

같은지를 비교하지 않고 서명을 확인하는 이유는, 인증 서버의 인증서에 유효 기간이 있어서 주기적으로 교체되기 때문이다. 상대의 인증서를 그대로 저장해 두고 비교하는 방식이라면 교체될 때마다 모든 기기의 저장본을 바꾸어야 한다. CA의 인증서를 저장해 두면 같은 CA가 서명한 새 인증서가 자동으로 통과된다.

상대의 인증서를 기억해 두고 같은지를 비교하는 방식도 존재한다. macOS가 처음 접속할 때 "이 인증서를 신뢰하겠습니까"라고 묻고, 승인된 인증서를 기억해 두는 동작이 이 방식에 가깝다. 서버처럼 사람이 화면을 보고 승인할 수 없는 기기에서는 CA의 인증서를 미리 넣어 두는 방식을 쓴다.

#### CA의 인증서 파일은 비밀이 아니다

| 항목                     | 내용                                    |
| ------------------------ | --------------------------------------- |
| 파일에 들어 있는 것      | CA의 이름, CA의 공개 열쇠, 유효 기간 등 |
| 파일에 들어 있지 않은 것 | CA의 비밀 열쇠. 발급 기관만 보관한다    |

비밀 열쇠가 들어 있지 않으므로, 이 파일은 다른 사람에게 전달하거나 서버에 저장해 두어도 문제가 없는 공개 정보이다.

#### 설정에 넣는 위치

서버의 Wi-Fi 설정 파일의 인증 항목에 파일의 경로를 한 줄로 적는다. 이 항목이 올바르게 인식되는 것은 서버의 임시 디렉터리에서 가짜 값으로 확인했다.

```yaml
      access-points:
        "corp_work":
          auth:
            key-management: eap
            method: peap
            phase2-auth: MSCHAPV2
            identity: "..."
            password: "..."
            ca-certificate: /etc/ssl/certs/corp-wifi-ca.pem   # CA 의 인증서 파일 경로 (경로는 예시)
```

#### 이 사례의 인증서

인증 서버가 보낸 인증서는 두 장이며, 서버의 연결 기록에 `depth` 값으로 구분되어 남는다.

| 기록의 표시 | 인증서의 이름                    | 역할                           |
| ----------- | -------------------------------- | ------------------------------ |
| `depth=0`   | `<제품명>`                       | 인증 서버 자신의 인증서        |
| `depth=1`   | `<제품명> Certificate Authority` | 위 인증서를 발급한 CA의 인증서 |

발급 기관의 이름으로 보아 이 인증서는 공인 기관이 아니라 접근 제어 제품에 내장된 자체 발급 기관이 만든 것으로 보인다. 이런 인증서는 기기의 신뢰 목록에 처음부터 들어 있지 않기 때문에 자동으로 검증할 수 없고, CA의 인증서 파일을 관리자에게서 받아야 한다.

## 5. 접근 제어 시스템 (NAC)

### 5.1 NAC가 하는 일

NAC(Network Access Control, 네트워크 접근 제어)는 네트워크에 연결된 기기가 통신해도 되는 기기인지를 검사하고, 통과하지 못한 기기의 통신을 제한하는 보안 시스템을 가리키는 제품 분류의 이름이다.

집에서는 Wi-Fi 비밀번호만 알면 어떤 기기든 연결되고 제한 없이 통신한다. 회사에서 이렇게 두면, 직원이 자신의 계정으로 개인 노트북이나 출처를 알 수 없는 기기를 연결했을 때 그 기기가 악성코드에 감염되어 있더라도 사내 서버에 그대로 접근할 수 있다. 그래서 회사 네트워크에는 검사가 두 단계로 존재한다.

```
[1단계: Wi-Fi 인증]                 [2단계: 기기 검사 — NAC 의 역할]

 ID·비밀번호가 맞는가?  ──통과──→   통신해도 되는 기기인가?  ──예────→  정상 통신
   ("누구인가"를 확인)               ("어떤 기기인가"를 확인)  └─아니오─→  통신 제한 + 안내 페이지로 이동
```

건물에 비유하면 1단계는 출입증으로 정문을 통과하는 것이고, 2단계는 건물 안의 보안 요원이 반입 신고가 되지 않은 장비를 발견해서 안내 데스크로만 가도록 막는 것이다.

### 5.2 NAC 제품의 구성 요소

NAC 제품은 대체로 다음과 같은 요소로 구성된다. 요소의 명칭은 제품마다 다를 수 있다.

```
                 ┌────────────────────┐
                 │ 정책 서버            │  모든 설정과 수집된 정보를 보관하고,
                 │ (Policy Server)    │  "어떤 기기를 허용할지"라는 규칙을 관리
                 └─────────┬──────────┘
                    규칙 전달 │ ↑ 수집한 정보 보고
                 ┌─────────┴──────────┐
                 │ 네트워크 센서         │  각 네트워크에 배치되어 연결된 기기를
                 │ (Network Sensor)   │  탐지하고, 규칙에 따라 통신을 제한
                 └─────────┬──────────┘
                    감시·제한 │
        ┌──────────────────┼──────────────────┐
     직원 노트북           휴대전화          새로 나타난 기기
   (에이전트 설치됨)                        (예: 서버의 무선 장치)
```

| 구성 요소     | 역할                                                                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정책 서버     | 규칙과 기기 정보를 보관하는 중앙 시스템                                                                                                                           |
| 네트워크 센서 | 네트워크에 연결된 기기를 찾아내고, 규칙을 위반한 기기의 통신을 실제로 막는 장치                                                                                   |
| 에이전트      | 직원의 PC에 설치하는 프로그램. 백신 설치 여부나 운영체제 업데이트 상태 같은 기기 내부의 정보를 정책 서버에 알려 준다. 설치를 요구하는지는 회사 정책에 따라 다르다 |

### 5.3 통신을 제한하는 방법

| 방법               | 동작 방식                                                                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ARP 방식의 차단    | 3.2절에서 본 것처럼 ARP에는 응답자를 검증하는 절차가 없다. 제한 대상 기기가 "gateway의 MAC 주소가 무엇인가"라고 물으면 센서가 "저입니다"라고 대신 응답해서, 그 기기가 보내는 통신이 실제 상대가 아닌 센서로 오도록 만든다 |
| 안내 페이지로 이동 | 제한된 기기가 웹 페이지를 열려고 하면 원래 사이트 대신 사내 안내 페이지를 보여 준다. 이 페이지를 CWP(Captive Web Portal)라고 하며, 기기 등록이나 에이전트 설치 같은 필요한 절차를 안내한다                                |

### 5.4 ZTNA

ZTNA(Zero Trust Network Access)는 "회사 네트워크 안에 있다는 이유만으로는 신뢰하지 않고, 접근할 때마다 사용자와 기기를 확인한다"라는 보안 방식을 가리킨다.

| 방식          | 사고방식                                         | 비유                                            |
| ------------- | ------------------------------------------------ | ----------------------------------------------- |
| 전통적인 방식 | 네트워크 안에 들어온 기기는 신뢰한다             | 정문만 통과하면 건물의 모든 방에 들어갈 수 있다 |
| Zero Trust    | 안에 있어도 신뢰하지 않고 접근할 때마다 확인한다 | 방마다 출입 권한과 반입 장비를 다시 확인한다    |

NAC 제품 중에는 NAC가 수집한 기기 정보를 바탕으로 접근 허용 여부를 결정하는 기능을 더해서 ZTNA 제품으로 확장된 것이 있다. 이 사례에서 인증 서버가 제시한 인증서의 이름에 "ZTNA"가 포함되어 있었으므로, 사내 접근 제어 제품은 이런 계열의 제품으로 보인다. 설치된 제품의 정확한 판은 확인되지 않았다.

Wi-Fi 인증 서버(4.3절)와 기기 검사를 같은 제품이 담당하는 구성이라면, 인증 서버가 "어느 계정으로 어떤 기기가 들어왔는지"를 접근 제어 쪽에 바로 알려 줄 수 있다. 이 부분은 구성에서 추론한 내용이며 실제 설정을 확인한 것은 아니다.

## 6. 작업 기록: 서버를 Wi-Fi에 연결하기

### 6.1 사전 조사

설정을 변경하기 전에 읽기 전용 명령으로 현재 상태를 파악했다. 모두 `sudo` 없이 실행된다.

```bash
ip -br link                 # 네트워크 장치 목록과 켜짐/꺼짐 상태
ip -br addr                 # 장치별 IP 주소
ip route                    # 경로 (어느 목적지를 어느 장치로 보내는가)
networkctl list             # 각 장치를 누가 관리하는가
systemctl is-active NetworkManager systemd-networkd wpa_supplicant
lspci -k | grep -iA3 network   # 무선 하드웨어와 드라이버
ping -c 2 1.1.1.1           # 인터넷 연결 여부
```

조사에서 확인된 사실은 다음과 같다.

- 유선은 이미 인터넷에 연결되어 있었고, 무선 장치는 꺼져 있었지만 하드웨어와 드라이버는 정상적으로 인식되어 있었다.
- 무선 설정에는 `sudo`가 필요한데 이 계정은 비밀번호를 요구한다. 그래서 설정 스크립트를 준비해 두고 서버의 소유자가 직접 실행하는 방식을 택했다. 이 방식에서는 `sudo` 비밀번호와 Wi-Fi 계정 정보가 대화나 명령 기록에 남지 않는다.
- 기존 설정 파일(`/etc/netplan/01-netcfg.yaml`)은 root만 읽을 수 있다. 현재 적용 중인 구성이 이 파일보다 나중에 생성된 것을 확인해서, 설정을 다시 적용하더라도 유선 구성이 바뀌지 않는다고 판단했다.

유선을 대체하는 것이 목적이므로 작업 순서를 다음과 같이 정했다. 무선으로 접속되는 것을 확인하기 전에 유선을 끊으면 원격으로 복구할 방법이 없어지기 때문이다.

```
1) 유선 유지한 채 무선 연결  →  2) 무선 IP로 SSH 접속 확인  →  3) 유선 설정 제거·랜선 분리
        (현재 SSH 유지)              (새 경로 검증)                 (되돌리기 어려운 단계)
```

### 6.2 Wi-Fi의 인증 방식 확인

서버에서는 `sudo` 없이 무선 탐색을 할 수 없어서, 같은 Wi-Fi가 저장되어 있는 Mac에서 확인했다. macOS는 Wi-Fi 이름을 가려서 표시하지만(`<redacted>`), 키체인에 저장된 항목의 **종류**로 인증 방식을 알 수 있다. 아래 명령은 비밀번호 값을 조회하지 않고 항목의 종류만 출력한다.

```bash
security find-generic-password -l corp_work | grep -E '"desc"|"svce"'
```

| 출력된 종류                | 의미                                       |
| -------------------------- | ------------------------------------------ |
| `802.1X Password`          | 회사 인증 방식 (ID와 비밀번호를 함께 입력) |
| `AirPort network password` | 일반 방식 (비밀번호 하나만 입력)           |

`corp_work`는 `802.1X Password`로 저장되어 있었으므로 회사 인증 방식이다.

### 6.3 설정 방식과 스크립트

기존 유선 설정 파일은 수정하지 않고, Wi-Fi 설정을 별도 파일(`/etc/netplan/60-wifi-corp.yaml`)로 추가한다. 문제가 생기면 그 파일만 삭제해서 되돌릴 수 있다. 추가되는 설정의 내용은 다음과 같다.

```yaml
network:
  version: 2
  wifis:
    wlp3s0:
      dhcp4: true
      dhcp4-overrides:
        route-metric: 600          # 무선 경로의 우선순위를 낮추어, 유선이 주 경로로 유지되게 한다
      access-points:
        "corp_work":
          auth:
            key-management: eap    # 회사 인증 방식(802.1X)
            method: peap
            phase2-auth: MSCHAPV2
            identity: "<개인 로그인 ID>"
            password: "<비밀번호>"
```

`route-metric`은 같은 목적지로 가는 경로가 여러 개일 때의 우선순위이며, 숫자가 작을수록 먼저 사용된다. 유선의 기본 경로에는 이 값이 지정되어 있지 않아서(0으로 취급) 유선이 계속 주 경로로 쓰인다.

설정 문법은 실제 설정 디렉터리를 건드리지 않고 임시 디렉터리에서 검증할 수 있다. `sudo`가 필요하지 않다.

```bash
D=$(mktemp -d); mkdir -p $D/etc/netplan
# 검증할 YAML 을 $D/etc/netplan/ 아래에 두고
netplan generate --root-dir $D
cat $D/run/netplan/wpa-wlp3s0.conf      # 변환된 Wi-Fi 설정 확인
```

#### 연결 스크립트 `~/wifi-setup.sh`

```bash
#!/usr/bin/env bash
# dev-server 를 corp_work Wi-Fi(802.1X)에 연결한다. 유선 설정은 건드리지 않는다.
# 실행: ssh -t dev-server 'sudo bash ~/wifi-setup.sh'
# 실패하면 추가한 설정 파일을 지우고 원래 상태로 되돌린다.
set -euo pipefail
trap '' HUP # netplan apply 도중 SSH 가 끊겨도 끝까지 실행해 결과 로그를 남긴다

IFACE=wlp3s0
SSID=corp_work
EAP_METHOD=${EAP_METHOD:-peap}
PHASE2=${PHASE2:-MSCHAPV2}
CONF=/etc/netplan/60-wifi-corp.yaml
UNIT=netplan-wpa-$IFACE.service
OWNER=${SUDO_USER:-root}
LOG=$(getent passwd "$OWNER" | cut -d: -f6)/wifi-setup.log
WAIT_SEC=90

[[ $EUID -eq 0 ]] || { echo "sudo 로 실행해야 합니다: sudo bash $0" >&2; exit 1; }
[[ -t 0 ]] || { echo "입력을 받을 터미널이 필요합니다 (ssh -t 로 접속)." >&2; exit 1; }
ip link show "$IFACE" >/dev/null

echo "$SSID 에 접속할 때 쓰는 개인 로그인 정보를 입력합니다 (Wi-Fi 이름이 아닙니다)."
read -r -p "개인 로그인 ID: " WIFI_ID
[[ $WIFI_ID != "$SSID" ]] || { echo "Wi-Fi 이름이 아니라 개인 로그인 ID 를 입력해야 합니다." >&2; exit 1; }
read -r -s -p "로그인 비밀번호: " WIFI_PW
echo
[[ -n $WIFI_ID && -n $WIFI_PW ]] || { echo "ID 와 비밀번호가 모두 필요합니다." >&2; exit 1; }

rollback() {
  systemctl stop "$UNIT" 2>/dev/null || true
  rm -f "$CONF"
  netplan apply
  ip link set "$IFACE" down 2>/dev/null || true
}

# 비밀번호가 ps 출력에 보이지 않도록 인자가 아니라 환경 변수로 넘긴다.
# JSON 문자열은 YAML 큰따옴표 문자열로도 유효하므로 특수문자를 json.dumps 로 처리한다.
umask 077
IFACE=$IFACE SSID=$SSID EAP_METHOD=$EAP_METHOD PHASE2=$PHASE2 WIFI_ID=$WIFI_ID WIFI_PW=$WIFI_PW \
  python3 - >"$CONF" <<'PY'
import json, os

e = os.environ
q = json.dumps
print(f"""network:
  version: 2
  wifis:
    {e['IFACE']}:
      dhcp4: true
      dhcp4-overrides:
        route-metric: 600
      access-points:
        {q(e['SSID'])}:
          auth:
            key-management: eap
            method: {e['EAP_METHOD']}
            phase2-auth: {e['PHASE2']}
            identity: {q(e['WIFI_ID'])}
            password: {q(e['WIFI_PW'])}""")
PY

if ! netplan generate; then
  rm -f "$CONF"
  echo "netplan 설정 검증에 실패해서 파일을 지웠습니다." >&2
  exit 1
fi

START=$(date +%s)
echo "설정을 적용합니다..."
netplan apply

wpa_log() { journalctl -u "$UNIT" --since "@$START" -o cat --no-pager; }

# 인증 실패가 한 번이라도 보이면 바로 멈춘다 (재시도가 쌓여 계정이 잠기는 것을 막는다).
result=timeout
for ((i = 0; i < WAIT_SEC; i += 2)); do
  if ip -4 -o addr show dev "$IFACE" scope global | grep -q inet; then
    result=ok
    break
  fi
  if wpa_log | grep -qE 'CTRL-EVENT-EAP-FAILURE|WRONG_KEY'; then
    result=auth_failed
    break
  fi
  sleep 2
done

{
  echo "result=$result method=$EAP_METHOD phase2=$PHASE2 at=$(date -Is)"
  echo "--- addr"
  ip -br addr show dev "$IFACE"
  echo "--- route"
  ip route show
  echo "--- wpa"
  wpa_log | while IFS= read -r line; do
    line=${line//"$WIFI_ID"/<id>}
    echo "${line//"$WIFI_PW"/<pw>}"
  done
} >"$LOG" 2>&1
chown "$OWNER": "$LOG"

if [[ $result == ok ]]; then
  echo "연결 성공: $(ip -br addr show dev "$IFACE")"
  echo "로그: $LOG"
else
  rollback
  echo "연결 실패($result). 추가한 설정을 지우고 되돌렸습니다. 로그: $LOG" >&2
  exit 1
fi
```

이 스크립트의 설계 의도는 다음과 같다.

| 처리                                                      | 이유                                                            |
| --------------------------------------------------------- | --------------------------------------------------------------- |
| ID와 비밀번호를 실행 중에 입력받는다                      | 비밀 정보가 명령 기록이나 대화에 남지 않게 한다                 |
| 설정 파일을 root만 읽을 수 있게 만든다 (`umask 077`)      | 비밀번호가 평문으로 저장되기 때문이다                           |
| 인증 실패가 한 번 감지되면 즉시 중단하고 되돌린다         | 잘못된 비밀번호로 재시도가 반복되어 계정이 잠기는 상황을 막는다 |
| 결과를 `~/wifi-setup.log`에 남긴다 (ID와 비밀번호는 가림) | `sudo` 없이도 결과를 읽고 원인을 판단할 수 있게 한다            |
| ID 자리에 Wi-Fi 이름을 입력하면 적용 전에 중단한다        | 6.4절의 첫 번째 실패에서 얻은 교훈이다                          |

#### 제거 스크립트 `~/wifi-remove.sh`

```bash
#!/usr/bin/env bash
# wifi-setup.sh 가 추가한 Wi-Fi 설정을 지우고, 유선만 쓰던 상태로 되돌린다.
# 실행: sudo ~/wifi-remove.sh
set -euo pipefail
trap '' HUP # netplan apply 도중 SSH 가 끊겨도 끝까지 실행한다

[[ $EUID -eq 0 ]] || { echo "sudo 로 실행해야 합니다: sudo bash $0" >&2; exit 1; }

systemctl stop "netplan-wpa-$IFACE.service" 2>/dev/null || true
rm -f "$CONF"

# 설정이 사라져도 이미 받은 주소·경로·DNS 가 남을 수 있어 직접 비운다.
ip addr flush dev "$IFACE" 2>/dev/null || true
ip link set "$IFACE" down 2>/dev/null || true
resolvectl revert "$IFACE" 2>/dev/null || true

echo "--- 무선 장치"

```

이 스크립트는 문법만 확인했고 실제로 실행해 보지는 않았다.

### 6.4 실행 결과와 로그 읽는 법

스크립트를 두 번 실행했다(시각은 서버 기준이며 UTC이다).

| 실행        | 입력한 ID                   | 결과                                              |
| ----------- | --------------------------- | ------------------------------------------------- |
| 1차 (01:22) | Wi-Fi 이름을 ID 자리에 입력 | ❌ 인증 실패. 스크립트가 자동으로 설정을 되돌렸다 |
| 2차 (01:32) | 개인 로그인 ID              | ✅ 인증 성공. `10.0.30.25/23`을 배정받았다        |

1차 실패의 원인은 입력 안내 문구("Wi-Fi 계정 ID")가 Wi-Fi 이름으로 읽힐 수 있었기 때문이다. 문구를 "개인 로그인 ID"로 고치고, Wi-Fi 이름이 입력되면 바로 중단하도록 수정했다.

연결 기록의 각 줄은 4.2절의 인증 순서와 다음과 같이 대응한다.

| 단계 | 기록에 남는 문구                                     | 의미                                                             |
| ---- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| ①    | `Associated with <공유기>`                           | 공유기와 무선으로 연결되었다. 아직 통신은 허용되지 않은 상태이다 |
| ②    | `CTRL-EVENT-EAP-STARTED`                             | 인증 절차가 시작되었다                                           |
| ③    | `EAP vendor 0 method 25 (PEAP) selected`             | PEAP 방식으로 합의했다                                           |
| ③    | `CTRL-EVENT-EAP-PEER-CERT depth=0 ... CN=<제품명>`   | 인증 서버가 인증서를 제시했다                                    |
| ④    | `EAP-MSCHAPV2: Authentication succeeded`             | ID와 비밀번호의 확인에 성공했다                                  |
| ⑤    | `CTRL-EVENT-EAP-SUCCESS`                             | 인증 서버가 통과를 통보했다                                      |
| ⑥    | `WPA: Key negotiation completed [PTK=CCMP GTK=CCMP]` | 이 기기 전용의 암호화 키가 만들어졌다                            |
|      | `CTRL-EVENT-CONNECTED`                               | 연결이 완료되었다                                                |

1차 실행에서는 ①부터 ③까지 똑같이 진행된 뒤, ④에서 아래와 같이 기록되고 중단되었다. 명부에 없는 ID였기 때문에 인증 서버가 거부한 것이다.

```
EAP-TLV: TLV Result - Failure
wlp3s0: CTRL-EVENT-EAP-FAILURE EAP authentication failed
wlp3s0: CTRL-EVENT-SSID-TEMP-DISABLED id=0 ssid="..." auth_failures=1 duration=10 reason=AUTH_FAILED
```

실패한 경우에도 기록은 유용한 정보를 준다. ③까지 진행되었다면 Wi-Fi 신호, 드라이버, 인증 방식(PEAP)에는 문제가 없고 계정 정보 쪽에 원인이 있다는 뜻이다. 인증 방식 자체가 맞지 않았다면 `method` 뒤의 숫자로 서버가 요구하는 방식을 알 수 있다(25는 PEAP, 21은 TTLS, 13은 TLS).

**인증서 검증에 대한 주의**: 이 설정에는 `ca-certificate` 항목이 없어서, 서버는 인증 서버의 인증서를 받아서 기록만 하고 검증하지 않는다(4.4절). 가짜 공유기에 대한 방어가 없는 상태이다.

## 7. 문제 진단: 연결은 되었는데 통신이 되지 않는다

### 7.1 경로별 시험 결과

Wi-Fi 연결에 성공한 뒤, 작업용 Mac에서 서버로 가는 네 가지 경로를 시험했다.

```
Mac 의 Wi-Fi                     목적지                     결과
────────────────────────────────────────────────────────────────────────────────
corp_admin (10.0.20.x) ──→  서버 유선 10.0.10.51   ✅ 정상 (기존에 사용하던 경로)
corp_admin (10.0.20.x) ──→  서버 무선 10.0.30.25   ❌ 요청이 서버에 도착하지 않음
corp_work  (10.0.30.x) ──→  서버 유선 10.0.10.51   ❌ gateway 에서 차단
corp_work  (10.0.30.x) ──→  서버 무선 10.0.30.25   ⚠️ ping 10회 중 2회만 성공, SSH 는 한 번 인증까지 된 뒤 멈춤
```

정상적으로 동작하는 접속 경로는 첫 번째 하나뿐이며, 이 경로는 유선에 의존한다. 따라서 이 상태에서 랜선을 제거하면 서버에 원격으로 접속할 방법이 없어진다.

`~/.ssh/config`의 접속 주소(`HostName`)를 무선 IP로 바꾸는 것만으로는 해결되지 않는다. 설정 파일을 수정하지 않고도 아래와 같이 같은 조건을 시험할 수 있는데, 무선 IP로는 연결 자체가 이루어지지 않았다. `HostKeyAlias`는 주소가 달라도 같은 서버인지를 기존에 저장된 서버 식별 정보로 확인하게 하는 옵션이다.

```bash
ssh -o HostName=10.0.30.25 -o HostKeyAlias=10.0.10.51 -o ConnectTimeout=8 dev-server hostname
```

### 7.2 사용한 진단 기법

#### 기법 1: 요청이 도착했는지를 수신 카운터로 확인한다

ping이 실패했을 때 원인은 둘 중 하나이다. 요청이 상대에게 도착하지 못했거나, 도착했는데 응답이 돌아오는 길에 유실된 것이다. 서버의 수신 카운터를 ping 전후로 읽으면 이 둘을 구분할 수 있다. 이 카운터는 `sudo` 없이 읽을 수 있다.

```bash
# 서버에서: 받은 ping 요청 수(InEchos)와 보낸 응답 수(OutEchoReps)
awk '/^Icmp:/{if(!h){split($0,k);h=1}else{for(i=2;i<=NF;i++)if(k[i]=="InEchos"||k[i]=="OutEchoReps")printf "%s=%s ",k[i],$i;print ""}}' /proc/net/snmp
```

| 실험 (Mac이 `corp_admin`에 있을 때)    | 서버의 수신 카운터 변화 |
| -------------------------------------- | ----------------------- |
| Mac에서 무선 IP로 ping 5회             | 0 증가                  |
| Mac에서 유선 IP로 ping 5회 (비교 기준) | 5 증가                  |
| 아무것도 보내지 않음 (잡음 확인)       | 0 증가                  |

요청이 도착했는데 응답만 유실된 것이라면 카운터는 증가했어야 한다. 전혀 증가하지 않았으므로 요청이 중간에서 차단되었다는 뜻이다. 비교 기준(유선 IP)과 잡음 확인을 함께 두어야 결과를 믿을 수 있다.

#### 기법 2: 경로 추적으로 어디에서 막히는지 본다

`traceroute`는 목적지까지 거치는 장비를 차례로 보여 준다. 정상적으로 응답하는 목적지와 나란히 비교하면 차단 여부가 드러난다.

| `corp_work`에서 경로 추적한 목적지   | gateway(`10.0.30.1`)의 응답 |
| ------------------------------------ | --------------------------- |
| 인터넷 주소 `1.1.1.1` (비교 기준)    | 응답함                      |
| 서버 유선 IP `10.0.10.51`            | 응답 없음                   |
| 서버 유선 대역의 gateway `10.0.10.1` | 응답 없음                   |

세 번째 목적지는 서버와 무관한 네트워크 장비인데도 응답이 없다. 따라서 `corp_work`에서 서버의 유선 대역으로 가는 통신은 서버의 설정과 관계없이 gateway에서 막히고 있다고 볼 수 있다. 사내 네트워크 정책에 따른 차단으로 해석되지만, 정책 내용을 직접 확인한 것은 아니다.

#### 기법 3: 같은 목적지로 유선과 무선을 나란히 측정한다

```bash
ping -I wlp3s0  -c 25 -W 1 1.1.1.1 &   # 무선
ping -I eno1.10 -c 25 -W 1 1.1.1.1 &   # 유선
wait
```

| 경로 | `1.1.1.1`로 ping 25회 |
| ---- | --------------------- |
| 유선 | 25회 성공             |
| 무선 | 0회 성공              |

같은 시간대에 같은 목적지로 보냈으므로, 차이의 원인은 무선 경로에 있다.

#### 기법 4: 특정 목적지만 막히는지 확인한다

무선으로 두 목적지에 동시에 ping을 보냈다.

| 무선으로 보낸 목적지               | 결과 (10회) |
| ---------------------------------- | ----------- |
| gateway `10.0.30.1`                | 0회 성공    |
| 같은 대역의 다른 주소 `10.0.30.10` | 10회 성공   |

전파 상태가 나쁘거나 무선 장치에 문제가 있다면 둘 다 유실되어야 한다. 한쪽만 유실되었으므로 특정 목적지를 선택적으로 막는 무엇인가가 있다는 뜻이다.

#### 기법 5: 웹 요청이 가로채지는지 확인한다

`http://1.1.1.1/`은 정상이라면 `https://1.1.1.1/`로 이동하라는 응답(301)을 준다. 같은 요청을 유선과 무선으로 각각 보냈다.

```bash
curl --interface eno1.10 -m 8 -s -o /dev/null -w "code=%{http_code} redirect=%{redirect_url}\n" http://1.1.1.1/
curl --interface wlp3s0  -m 8 -s -D - http://1.1.1.1/
```

| 경로 | 응답                                                                 |
| ---- | -------------------------------------------------------------------- |
| 유선 | `301`, `https://1.1.1.1/`로 이동 (실제 사이트의 응답)                |
| 무선 | `200`, 660바이트의 페이지. 사내 주소의 안내 페이지로 이동시키는 내용 |

무선으로 보낸 웹 요청에 실제 사이트가 아닌 사내 장비가 응답했고, 응답에 담긴 주소는 5.3절에서 설명한 안내 페이지(CWP)를 가리켰다. 이것이 접근 제어 시스템이 개입하고 있다는 직접적인 근거이다. 안내 페이지의 내용은 브라우저가 없어서 확인하지 못했다(명령줄로 요청하면 "세션이 만료되었습니다"라는 문구만 돌아온다).

#### 기법 6: 서버의 기록으로 접속 시도의 흔적을 찾는다

```bash
journalctl -u ssh --since "01:30" --no-pager | grep -E "10\.0\.3[01]\."
ss -tln | grep -E ":22\s"              # SSH 가 어느 주소에서 수신하는가
grep ENABLED /etc/ufw/ufw.conf         # 방화벽이 켜져 있는가
ip neigh show dev wlp3s0               # 무선 쪽에서 알고 있는 이웃 기기 (ARP 기록)
```

- SSH 기록에 `corp_work`의 Mac(`10.0.30.19`)에서 들어온 접속이 02:12에 한 번 인증까지 성공한 것으로 남아 있었다. 무선 IP로의 접속이 원천적으로 불가능한 것이 아니라, 제한이 적용되는 도중에 일부 통신이 통과했다는 뜻이다.
- SSH는 모든 주소(`0.0.0.0:22`)에서 수신하고 있고, 방화벽은 꺼져 있었다(`ENABLED=no`).
- 무선 쪽의 이웃 기록에서 gateway(`10.0.30.1`)와 다른 두 주소(`10.0.30.10`, `10.0.30.19`)가 모두 **하나의 MAC 주소**로 조회되었다. 3.1절의 관점에서 보면 "최종 목적지(IP)가 셋 중 누구든, 실제로 건네는 상대(MAC)는 같은 장치 하나"라는 뜻이다. 즉 서버가 다른 Wi-Fi 기기에게 보내는 데이터는 상대에게 직접 가지 않고 중간의 한 장치를 거친다. 이 모양은 5.3절의 ARP 방식의 차단과 비슷하지만, 접근 제어와 무관하게 gateway가 원래 그렇게 동작하도록 설정된 네트워크에서도 나타나므로 이것만으로는 근거가 되지 않는다.

### 7.3 시간에 따른 변화와 원인

| 시각 (서버 기준, UTC) | 무선 경로 상태     | 관측된 것                                                                      |
| --------------------- | ------------------ | ------------------------------------------------------------------------------ |
| 01:32 연결 직후       | 제한 전            | 서버에서 무선으로 인터넷에 ping 2회 모두 성공                                  |
| 02:12 무렵            | 제한이 적용되는 중 | ping 40~60% 유실. Mac에서 무선 IP로 SSH 접속이 한 번 인증까지 성공한 뒤에 멈춤 |
| 02:20 이후            | 제한 적용          | ping 100% 유실, 웹 요청은 안내 페이지로 이동                                   |

**결론**: 서버의 무선 장치는 Wi-Fi 인증(5.1절의 1단계)을 통과했지만, 그 뒤에 사내 접근 제어 시스템의 제한 대상으로 처리되어(2단계) 통신이 차단되었다. 서버나 PC의 설정으로 해결할 수 있는 문제가 아니다.

| 구분             | 내용                                                                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 관측한 사실      | 무선으로 보낸 웹 요청이 사내 안내 페이지로 이동된다. 유선으로 보낸 같은 요청은 정상이다. Wi-Fi 인증 서버의 인증서 이름이 접근 제어 제품의 이름이다 |
| 해석             | 접근 제어 시스템이 서버의 무선 장치를 제한하고 있다                                                                                                |
| 확인하지 못한 것 | 어떤 규칙에 해당되어 제한되었는지(미등록 기기, 에이전트 미설치 등), 승인에 필요한 조건이 무엇인지. 네트워크 관리자만 확인할 수 있다                |

연결 직후에만 통신이 되었던 점에 주의해야 한다. 연결 직후의 시험 결과만 보고 "정상"이라고 판단하면, 나중에 제한이 적용된 뒤의 상태를 놓치게 된다.

### 7.4 확인해서 배제한 원인 후보

| 후보                                                       | 배제한 근거                                                                             |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 서버의 방화벽이 무선 쪽 접속을 막는다                      | 방화벽이 꺼져 있고, 차단 기록이 없으며, SSH가 모든 주소에서 수신한다                    |
| 무선 신호가 약하거나 무선 장치의 절전 동작 때문에 유실된다 | 신호 세기가 양호하고(-51~-53 dBm), 같은 무선으로 보낸 `10.0.30.10`은 10회 모두 성공했다 |
| 접속 주소(`HostName`)가 옛 주소를 가리킨다                 | 무선 IP를 직접 지정해서 접속해도 연결되지 않았다                                        |
| Wi-Fi 인증 방식을 잘못 가정했다                            | PEAP + MSCHAPv2로 인증에 성공했다                                                       |

### 7.5 유선과 무선을 함께 연결했을 때 달라지는 점

두 연결을 함께 유지하는 것 자체는 가능하다. 유선이 주 경로이고 무선은 우선순위가 낮은 경로로 대기한다. 다만 다음과 같은 차이가 생긴다.

| 달라지는 점                            | 설명                                                                                                                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DNS 서버로 가는 통신이 무선으로 나간다 | Wi-Fi가 DNS 서버 주소(통신사의 공개 DNS, `8.8.8.8`)와 함께 그 주소로 가는 전용 경로를 내려 준다. 그래서 이 주소들로 가는 통신은 우선순위와 관계없이 무선을 사용한다. 무선이 제한된 뒤에는 `8.8.8.8`로 보내는 ping이 100% 유실되었다(DNS 조회 자체는 응답을 받았다) |
| 계정 정보가 서버에 저장된다            | 입력한 ID와 비밀번호가 `/etc/netplan/60-wifi-corp.yaml`에 평문으로 저장된다. root만 읽을 수 있다                                                                                                                                                                   |
| 무선 IP가 바뀔 수 있다                 | DHCP로 받은 주소이기 때문이다 (3.3절)                                                                                                                                                                                                                              |

특정 주소로 가는 통신이 어느 장치를 사용하는지는 다음 명령으로 확인한다.

```bash
ip route get 8.8.8.8     # → dev wlp3s0 (무선)
ip route get 1.1.1.1     # → dev eno1.10 (유선)
```

## 8. 유선을 무선으로 대체하려면 필요한 것

서버의 무선 장치를 접근 제어 시스템에 등록하는 것만으로는 목표가 완성되지 않는다. 보안팀(네트워크 관리자)에게 요청해야 하는 항목은 다음과 같다.

| #   | 요청 항목                                                      | 요청하지 않으면 생기는 일                                                                                                                                                                        | 필요성 |
| --- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| 1   | 서버의 무선 장치(MAC `aa:bb:cc:dd:ee:ff`)를 승인된 기기로 등록 | 통신이 제한된다 (현재 상태)                                                                                                                                                                      | 필수   |
| 2   | 그 장치에 항상 같은 IP를 배정 (DHCP 예약)                      | IP가 바뀌면 접속 주소가 무효가 된다                                                                                                                                                              | 필수   |
| 3   | `corp_admin`에서 서버의 무선 IP로 SSH 접속 허용                | Wi-Fi 연결이 되어도 작업용 PC에서 접속할 수 없다. 연결 직후에 시험했을 때 요청이 서버에 도착하지 않았다                                                                                          | 필수   |
| 4   | 개인 계정 대신 서버 전용 Wi-Fi 계정 발급                       | 서버는 다시 연결할 때마다 저장된 ID와 비밀번호로 인증을 거친다. 개인 계정의 비밀번호를 변경하면 서버의 Wi-Fi가 끊기고, 유선이 없는 상태라면 서버에 직접 모니터와 키보드를 연결해서 복구해야 한다 | 권장   |
| 5   | Wi-Fi 인증 서버의 CA 인증서 파일 제공                          | 서버가 인증 서버의 진위를 확인하지 못한다 (4.4절). 연결 자체에는 필요하지 않다                                                                                                                   | 권장   |

기기를 등록할 때에는 반드시 **무선 장치**의 MAC 주소를 전달해야 한다. 유선 장치는 MAC 주소가 다르다.

```bash
ssh dev-server 'ip link show wlp3s0'                 # link/ether 뒤의 값
ssh dev-server 'cat /sys/class/net/wlp3s0/address'   # 값만 한 줄로
```

```
3: wlp3s0: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
    link/ether aa:bb:cc:dd:ee:ff brd ff:ff:ff:ff:ff:ff
               └──── 이 값 ────┘   (brd 뒤의 ff:ff:… 는 "모두에게 보낼 때 쓰는 주소"이며 MAC 주소가 아니다)
```

**요청 방식**: 항목을 나열해서 요청하기보다는, 목표를 먼저 설명하고 적절한 방법을 묻는 편이 낫다. 직원용 Wi-Fi는 직원의 기기를 위한 네트워크로 설계되어 있을 가능성이 높아서, 보안팀이 서버용 네트워크를 따로 안내하거나 다른 방법을 제시할 수도 있기 때문이다. 위 표는 Wi-Fi 연결이 허용되었을 때 빠뜨리지 않고 확인할 목록으로 쓴다.

```
개발 서버(<서버 이름>)를 랜선 없이 Wi-Fi 로 운영하려고 합니다.
직원용 Wi-Fi 에 연결해 보았는데, 인증은 통과했지만 접근 제어 안내 페이지로 이동되면서
통신이 제한되었습니다. 서버를 무선으로 운영할 수 있는 방법이 있는지 문의드립니다.

가능하다면 아래 사항이 필요합니다.
1. 서버 무선 장치(MAC <무선 장치의 MAC 주소>)의 기기 등록·승인
2. 해당 장치에 고정 IP 배정
3. 관리용 Wi-Fi 에서 그 IP 로의 SSH(22번 포트) 접속 허용
4. 서버 전용 Wi-Fi 계정 발급 (현재는 개인 계정으로 시험했습니다)
5. Wi-Fi 인증 서버의 CA 인증서 파일
```

**승인을 받은 뒤의 작업 순서**

```
① 보안팀의 승인·설정 완료  →  ② wifi-setup.sh 로 다시 연결  →  ③ 무선 IP 로 SSH 접속 확인
   →  ④ ~/.ssh/config 의 HostName 변경  →  ⑤ 유선 설정 제거·랜선 분리
```

- ②에서 서버 전용 계정과 CA 인증서를 사용하려면 `wifi-setup.sh`에 `ca-certificate` 줄을 추가해야 한다.
- ③이 확인되기 전에는 유선을 제거하지 않는다. 연결 직후뿐 아니라 시간이 지난 뒤에도 통신이 유지되는지 확인해야 한다(7.3절).
- 현재 유선 주소(`10.0.10.51`)로 이 서버를 사용하는 다른 사람이나 시스템이 있다면, 유선을 제거한 뒤에는 그쪽에서도 새 주소로 접속할 수 있어야 한다. 누가 이 서버에 접속하는지는 따로 확인해야 한다.

## 10. 주의점 모음

1. **무선으로 접속되는 것을 확인하기 전에 유선을 끊지 않는다.** 새 경로가 검증되지 않은 상태에서 기존 경로를 제거하면 원격으로 복구할 수 없다.
2. **연결 직후의 결과만으로 정상이라고 판단하지 않는다.** 접근 제어 시스템의 제한은 연결하고 나서 시간이 지난 뒤에 적용될 수 있다.
3. **Wi-Fi 인증 통과와 통신 허용은 별개이다.** 회사 네트워크에는 계정 확인과 기기 검사라는 두 단계가 있다.
4. **ID 입력란에는 Wi-Fi 이름이 아니라 개인 로그인 ID를 넣는다.**
5. **잘못된 비밀번호로 재시도가 반복되지 않게 한다.** 계정이 잠길 수 있다.
6. **ping의 성공과 실패를 서비스의 동작 여부로 바로 연결하지 않는다.** 신호의 종류에 따라 허용 여부가 다를 수 있다.
7. **시험할 때에는 비교 기준을 함께 둔다.** 정상인 경로(유선)나 정상인 목적지(`1.1.1.1`)와 나란히 측정해야 결과를 해석할 수 있다.
8. **한 번에 한 가지만 바꾸어 시험한다.** 숫자 주소로 ping을 보내서 DNS를 분리하는 것, 같은 목적지로 경로만 바꾸는 것이 그 예이다.
9. **사람이 아닌 서버에는 개인 계정을 쓰지 않는 것이 좋다.** 비밀번호 변경이 서버의 연결 끊김으로 이어진다.
10. **고정 IP를 서버에 직접 입력할 때에는 관리자와 협의한다.** 자동 배정 범위와 겹치면 주소가 충돌한다.
11. **인증서 검증을 생략한 설정은 가짜 공유기에 대한 방어가 없다.**

## 11. 용어 정리

| 용어                     | 뜻                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| IP 주소                  | 데이터의 최종 목적지를 나타내는 주소                                                            |
| MAC 주소                 | 장치마다 정해져 있는 고유 번호. 바로 옆 장치에게 데이터를 건넬 때 쓴다                          |
| 대역 (서브넷)            | 같은 네트워크에 속하는 IP 주소의 범위                                                           |
| gateway                  | 다른 대역으로 나가는 관문 역할의 장비                                                           |
| ARP                      | IP 주소로 MAC 주소를 알아내는 규약                                                              |
| DHCP                     | IP 주소 등 통신 설정을 자동으로 나누어 주는 규약                                                |
| DHCP 예약                | 특정 MAC 주소에 항상 같은 IP를 배정하도록 DHCP 서버에 등록하는 것                               |
| DNS                      | 이름(예: `example.com`)을 IP 주소로 바꾸어 주는 서비스                                          |
| ping                     | 상대가 응답하는지와 응답 시간을 측정하는 도구                                                   |
| ICMP / TCP               | 통신 신호의 종류. ping은 ICMP를, SSH와 웹은 TCP를 쓴다                                          |
| 802.1X (WPA2 Enterprise) | 사용자마다 다른 ID와 비밀번호로 인증하는 회사용 Wi-Fi 방식                                      |
| RADIUS                   | 공유기와 인증 서버가 통신하는 규약. 인증 서버 자체를 가리키기도 한다                            |
| EAP / PEAP / MSCHAPv2    | 802.1X 인증 대화의 규약 / 암호화 통로를 먼저 만드는 방식 / 비밀번호를 보내지 않고 확인하는 방식 |
| 인증서                   | 공개 열쇠, 주인의 이름, 발급 기관의 서명을 묶은 문서                                            |
| CA                       | 인증서를 발급하는 기관                                                                          |
| NAC                      | 연결된 기기를 검사하고 통과하지 못한 기기의 통신을 제한하는 보안 시스템                         |
| CWP                      | 제한된 기기에게 보여 주는 안내 페이지                                                           |
| ZTNA                     | 네트워크 안에 있어도 신뢰하지 않고 접근할 때마다 확인하는 보안 방식                             |
| netplan                  | Ubuntu에서 네트워크 설정을 YAML 파일로 관리하는 도구                                            |
| wpa_supplicant           | 리눅스에서 Wi-Fi 연결과 인증을 담당하는 프로그램                                                |
| route metric             | 같은 목적지로 가는 경로가 여러 개일 때의 우선순위. 작을수록 먼저 쓴다                           |

## 12. 명령어 모음

모두 `sudo` 없이 실행된다(별도로 표시한 것은 제외).

| 목적                                   | 명령                                                                 |
| -------------------------------------- | -------------------------------------------------------------------- |
| 장치 목록과 상태                       | `ip -br link`                                                        |
| 장치별 IP 주소                         | `ip -br addr`                                                        |
| 경로 전체                              | `ip route`                                                           |
| 특정 주소가 어느 장치로 나가는가       | `ip route get 8.8.8.8`                                               |
| 무선 장치의 MAC 주소                   | `cat /sys/class/net/wlp3s0/address`                                  |
| 이웃 기기 (ARP 기록)                   | `ip neigh show dev wlp3s0` (Mac에서는 `arp -n <IP>`)                 |
| 장치별 관리 상태와 받은 주소           | `networkctl status wlp3s0`                                           |
| DHCP로 받은 정보                       | `cat /run/systemd/netif/leases/$(cat /sys/class/net/wlp3s0/ifindex)` |
| 장치를 지정해서 ping                   | `ping -I wlp3s0 -c 10 1.1.1.1`                                       |
| 경로 추적                              | `traceroute -n 1.1.1.1`                                              |
| 장치를 지정해서 웹 요청                | `curl --interface wlp3s0 -m 8 -s -D - http://1.1.1.1/`               |
| DNS 조회 (장치 지정)                   | `resolvectl query -i wlp3s0 example.org`                             |
| Wi-Fi 연결 기록                        | `journalctl -u netplan-wpa-wlp3s0.service --no-pager`                |
| SSH 접속 기록                          | `journalctl -u ssh --no-pager`                                       |
| SSH가 수신하는 주소                    | `ss -tln \| grep ':22'`                                              |
| 방화벽이 켜져 있는가                   | `grep ENABLED /etc/ufw/ufw.conf`                                     |
| 받은 ping 요청 수                      | `grep -A1 '^Icmp:' /proc/net/snmp`                                   |
| netplan 설정 문법 검증 (임시 디렉터리) | `netplan generate --root-dir <임시 디렉터리>`                        |
| 접속 주소만 바꾸어 SSH 시험 (PC에서)   | `ssh -o HostName=<IP> -o HostKeyAlias=<기존 IP> dev-server hostname` |
| Wi-Fi 인증 방식 확인 (Mac에서)         | `security find-generic-password -l <Wi-Fi 이름> \| grep '"desc"'`    |
| Wi-Fi 연결 (`sudo` 필요)               | `ssh -t dev-server 'sudo ~/wifi-setup.sh'`                           |
| Wi-Fi 설정 제거 (`sudo` 필요)          | `ssh -t dev-server 'sudo ~/wifi-remove.sh'`                          |
