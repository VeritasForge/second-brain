# 루브릭(Rubric)이란 무엇인가

## 배경: 이 용어를 어디서 마주쳤나

`compound-engineering` 플러그인의 `ce-resolve-pr-feedback` 스킬(PR 리뷰 코멘트를 자동으로 판단·수정·resolve하는 스킬)을 분석하던 중, 오케스트레이터가 각 리뷰 코멘트의 타당성을 판정하는 데 쓰는 `references/evaluation-rubric.md` 파일을 발견했다. 이 "루브릭"이라는 표현이 낯설어서 개념을 짚고 넘어가게 되었다.

---

## 1. 정의와 어원 — AI가 만든 용어가 아니다

**한 줄 정의**: 무언가의 품질을 "감(느낌)"이 아니라 **정해진 평가 기준 + 각 기준별 판정 결과**로 나누어 판단하게 해주는 채점/판단 가이드.

| 시기         | 어디서 쓰였나 |
| ------------ | ------------- |
| 중세         | 라틴어 `rubrica`(붉은 흙, 적토) → 필사본에서 지시문·제목을 빨간 잉크로 써넣은 부분을 "rubric"이라 부름 |
| 20세기 중반~ | 미국 교육 현장에서 "에세이 채점 기준표"를 rubric이라 부르기 시작 (교사들이 채점자마다 기준이 달라 점수가 들쑥날쑥한 문제를 해결하려고 도입) |
| 최근 (LLM 시대) | "LLM-as-judge" 평가 방식에서 그대로 재사용 — AI 모델의 답변을 다른 AI가 채점할 때 "이 기준으로 판단해라"라는 규칙표를 rubric이라 부름 |

즉, **AI가 만든 용어가 아니라 교육 평가 분야에서 수십 년간 쓰이던 용어를, AI 평가(eval) 분야가 그대로 빌려 쓴 것**이다.

### 교육 현장의 실제 예시

```text
📝 에세이 채점 루브릭 예시

| 평가 기준        | 1점 (미흡)          | 3점 (보통)            | 5점 (우수)              |
|------------------|--------------------|-----------------------|-------------------------|
| 논리 전개        | 주장이 없음         | 주장은 있으나 근거 약함 | 주장+근거+반론까지 있음  |
| 문법/맞춤법      | 오류 다수           | 간단한 오류 몇 개       | 오류 없음                |
| 창의성           | 상투적 표현         | 부분적으로 독창적       | 독창적 관점               |
```

채점자가 3명이어도 이 표만 있으면 누가 채점해도 비슷한 점수가 나오도록 만드는 게 목적이다 — "판단 기준을 사람 머릿속에서 문서로 꺼내놓는다"는 게 rubric의 핵심 역할이다.

## 2. LLM 분야에서의 활용

```text
[교육 현장]                        [LLM 평가 (LLM-as-judge)]
교사가 학생 에세이를 채점    ≈    심판 역할의 LLM이 다른 LLM의 답변을 채점
     │                                    │
     ▼                                    ▼
"논리 전개 / 문법 / 창의성"   ≈    "정확성 / 안전성 / 유용성" 같은 기준표
각 기준에 1~5점 배점                각 기준에 pass/fail 또는 점수 배점
```

**LLM** (Large Language Model, 대규모 언어 모델) 벤치마크(MT-Bench, HELM 등)에서 모델 답변을 다른 모델이 채점할 때, "이 기준으로 판단하라"는 rubric을 프롬프트에 박아넣는 방식이 대표적 응용이다.

### `ce-resolve-pr-feedback`의 루브릭과의 대응

| 교육 현장 루브릭                          | `ce-resolve-pr-feedback`의 루브릭 |
| ------------------------------------------ | ---------------------------------- |
| 평가 대상 = 학생의 에세이                  | 평가 대상 = 리뷰어가 남긴 코멘트 1건 |
| 기준 = 논리/문법/창의성                    | 기준 = "지적이 코드로 확인되는가", "고치면 더 나빠지는가", "위험을 감당 가능한가" 등 |
| 점수 = 1~5점                               | 판정(verdict) = `fixed` / `not-addressing` / `declined` / `replied` / `needs-human` 중 하나 |
| 목적 = 채점자마다 기준이 다른 문제 방지    | 목적 = 봇이든 사람이든, 코멘트 형태가 뭐든 같은 기준으로 판단해서 일관성 확보 |

**참고 인접 용어**: "scoring guide", "grading criteria", "evaluation criteria", "decision matrix". AI 평가 커뮤니티에서는 특히 "LLM-as-judge rubric", "eval rubric"이라는 표현을 자주 쓴다.

## 3. Rubric과 Golden Set의 관계

**Golden Set** = "정답이 뭔지" 미리 정해둔 참조 데이터(입력+정답 쌍의 모음). "골든 셋은 루브릭을 통과한 정답지"라는 프레이밍은 완전히 틀린 건 아니지만, **인과관계가 상황에 따라 반대로 놓일 수 있어** 정정이 필요하다.

| 개념                     | 역할                                       | 질문으로 치면       |
| ------------------------ | ------------------------------------------ | -------------------- |
| **골든 셋 (Golden Set)** | "정답이 뭔지" 미리 정해둔 참조 데이터       | "정답이 무엇인가?"   |
| **루브릭 (Rubric)**      | 그 정답 여부나 품질을 어떻게 판단할지의 기준 | "어떻게 판단할 것인가?" |

### 세 가지 채점 방식

```text
[방식 A] Reference 기반 채점 — 골든 셋과 "직접" 비교, 루브릭이 아예 없을 수도 있음
──────────────────────────────────────────────────────────
모델 답변 ─────────────┐
                        ├──▶ [문자열 일치 / 유사도 비교] ──▶ Pass / Fail
골든 셋의 정답 ──────────┘
   예: "2+2는?" 같은 사실형 질문 → 정답이 명확해서 기준표 없이 그냥 대조


[방식 B] Rubric 기반 채점 — 골든 셋이 아예 없을 수도 있음, 기준표 자체로 채점
──────────────────────────────────────────────────────────
모델 답변 ──▶ [심사자(사람 또는 심사 LLM)] ──▶ 점수/판정
                    ▲
                    │ 참고
              [루브릭: "정확한가? 안전한가? 어조가 적절한가?"]
   예: "이 이메일 초안 어때?" 같은 개방형 질문 → 유일한 정답이 없어서 기준으로만 채점


[방식 C] 혼합 (실무에서 흔함) — 루브릭 "안에" 골든 셋 대조가 기준 중 하나로 포함됨
──────────────────────────────────────────────────────────
루브릭 예시:
  1. 골든 셋의 핵심 사실(fact)과 일치하는가?  ← 여기서만 골든 셋을 "참조"
  2. 불필요한 장황함이 없는가?
  3. 어조가 적절한가?
```

핵심은 (C)이다 — 루브릭의 여러 판정 기준 중 **하나로** "골든 셋과 일치하는지"가 들어갈 수는 있지만, 그건 "골든 셋이 루브릭을 통과해서 만들어진 것"이 아니라 **거꾸로 루브릭이 골든 셋을 참조 재료로 쓰는 것**이다.

### 단, 골든 셋을 "만들 때"는 사용자 말이 맞을 수 있다

- 전문가가 "이 답변을 정답으로 인정할지" 결정할 때 체크리스트(=루브릭과 거의 같은 것)를 쓴다. 예: "사실이 정확한가 / 완결성이 있는가 / 편향이 없는가"를 통과해야 골든 셋에 편입.
- 이 **구축(curation) 단계**에서는 "루브릭을 통과한 답만 골든 셋에 들어간다"는 프레이밍이 정확하다.
- 다만 이건 구축 단계에만 성립하고, **골든 셋을 평가에 활용하는 단계**에서는 관계가 반대(루브릭이 골든 셋을 참조)로 바뀐다.

**어원도 방향을 보여준다**: "golden"은 "gold standard(금본위 표준)"에서 온 말로 — 원래 의학 진단에서 "가장 신뢰할 수 있는 기준 검사"를 뜻하던 표현이다. "무언가를 통과해서 금이 된" 게 아니라 "그 자체로 가장 믿을 만한 기준"이라는 뜻이라, 애초에 "루브릭 통과작"이라는 의미가 어원에도 없다.

## 4. 생성 기준 vs 평가 기준 — Rubric이라 부를 수 있는 경계

"판단 기준"이라는 말은 **두 개의 서로 다른 시점**을 가리킬 수 있어서, 그걸 구분하지 않으면 rubric이라는 단어를 써도 되는지 애매해진다.

```text
[생성 전 기준]                         [생성 후 기준]
"카드를 어떻게 만들어야 하는가"    vs   "만들어진 카드가 잘 됐는가"
       │                                       │
       ▼                                       ▼
템플릿 / 스키마 / 스펙                    루브릭(Rubric)
(무엇을 채워 넣을지 규정)               (품질을 어떻게 판정할지 규정)
```

- **생성 전(사전) 기준** — "업무 카드에는 제목·담당자·마감일·완료조건이 반드시 들어가야 한다" → **템플릿(template)** 또는 **스키마(schema)**, **스펙(spec)**에 더 가깝다. "무엇을 만들지"를 규정하는 것이지, "잘 만들어졌는지 채점"하는 게 아니기 때문이다.
- **생성 후(사후) 기준** — "만들어진 카드가 제목이 명확한가? 담당자가 애매하지 않은가? 완료조건이 측정 가능한가?"를 놓고 품질을 판정 → 이게 원래 의미의 **루브릭**이다.

### 실무 인접 용어 비교

| 용어                                                   | 무엇을 규정하는가                          | 언제 쓰이나         | 형태                              |
| ------------------------------------------------------- | ------------------------------------------- | -------------------- | ---------------------------------- |
| **템플릿 / 스키마**                                     | 카드에 들어갈 필드·구조 (제목, 담당자, 마감일...) | 생성 시점            | "이 필드가 있어야 한다" (구조 규정) |
| **Acceptance Criteria (수용 기준) / DoD (Definition of Done, 완료 정의)** | 이 카드가 "완료됐다"고 인정할 조건          | 생성 시점~완료 판정 | "~하면 완료로 본다" (조건 나열, 애자일에서 흔히 씀) |
| **스타일 가이드 / 작성 가이드라인**                      | 문체·톤·표현 규칙                           | 생성 시점            | "이렇게 써라" (작성 규칙)          |
| **루브릭 (Rubric)**                                     | 생성된 결과물의 품질을 등급/점수로 판정      | 생성 후(사후 평가)   | "이 기준으로 몇 점/pass-fail인지 매긴다" (판정) |

특히 **Acceptance Criteria/DoD**가 "업무 카드"라는 도메인(프로젝트/작업 관리)에서는 rubric보다 훨씬 더 흔하게 쓰이는 표준 용어다 — 애자일(Agile)/스크럼(Scrum)에서 "이 작업이 완료됐다고 볼 조건"을 정의할 때 정확히 이 단어를 쓴다.

### 자동 생성 워크플로우 설계 시 실무 패턴

자동 생성 워크플로우라면, 아래처럼 두 단계로 나누는 게 실무적으로 흔한 패턴이다:

```text
[1단계: 생성]                    [2단계: 자기 검증(rubric)]
입력(요청/맥락)                        │
   │                                   │
   ▼                                   ▼
LLM이 템플릿/스키마에 맞춰      생성된 카드를 rubric으로 채점
카드 초안 생성                  ("제목이 구체적인가?" "완료조건이
   │                             측정 가능한가?" 등 기준별 pass/fail)
   └──────────────┬────────────────────┘
                   ▼
          Pass → 카드 확정
          Fail → 어느 기준에서 걸렸는지 사유와 함께 재생성
```

이렇게 나누면 **템플릿/스키마** = "카드가 뭘 담아야 하는가"(구조), **루브릭** = "생성된 카드가 그 구조를 잘 충족했는가"(품질 자기검증)로 역할이 분리되어, "생성 → 자체 채점 → 재시도" 루프를 설계할 때 rubric이 정확히 어느 자리에 들어가는지 명확해진다.

## 5. 최종 정리 — Rubric인지 아닌지 판별하는 한 줄 규칙

> **Rubric의 핵심 조건은 "판정 대상이 이미 존재해야 한다"는 것.** 무언가를 채점·판정하려면 채점할 결과물이 먼저 있어야 하기 때문이다.

| 상황                                     | Rubric인가?      | 이유                              |
| ----------------------------------------- | ----------------- | ---------------------------------- |
| 에세이/PR 코멘트/모델 답변을 채점         | ✅                 | 결과물이 존재 → 그걸 판정          |
| 업무 카드에 담을 필드를 규정              | ❌ (템플릿/스키마) | 아직 결과물이 없음 → 구조만 지정   |
| 생성된 업무 카드가 조건을 충족하는지 재검증 | ✅                 | 결과물이 존재 → 그걸 판정          |

**결론**: "Rubric = evaluation(평가)을 위한 채점/판정 기준"이 가장 정확한 정의다. "생성 전이냐 생성 후냐"만 물으면, 어떤 기준표가 rubric에 해당하는지 바로 판별할 수 있다.
